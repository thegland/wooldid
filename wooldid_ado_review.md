**Findings (Claude, 2026-09-05). Two independent investigations - an instrumented-worker probe and an outside-wooldid replication of the regression - each re-measured by an adversarial re-run on the working tree; every number below reproduced to all printed digits wherever it was re-run. Scratch: `~/.claude/jobs/be9644d0/tmp/{refmargin,modelconstruction,refute,refute-refmargin}/`. No repo file was touched by the probes. Line numbers refer to the current working tree.**

**Short answer.** No reported surface ever prints a non-zero reference-period effect: the event-study margins run over `subpop(targetflag==1 & _t in window)`, which excludes the reference cell; `e(b_es_*)` has no reference entry; the plots, the saved plot data and the adversarial line plant a zero at the reference relative year; the only margins sites that include `_t==0` are the `contrast(overjoint)` joint-test calls. The non-zero reference margin is nevertheless the symptom of two distinct defects, and the issue is NOT confined to the joint tests: for one mechanism the printed rows are wrong by a constant, for the other every reported row is a parameterisation artifact.

**When it comes up.** Under `interactivecontrols()` the reference-cell margin equals `-s000 x E_w[demeaned covariate | treated reference rows]`, where `s000` is the coefficient on the reference-cell slope column `0._i#0._t#0.targetflag#c.x_dm` that the cell interaction at ado ~1228 creates (`i.targetflag` includes its base level). It is non-zero exactly when that weighted mean is non-zero: a covariate that varies within cohort over time, weights, or an unbalanced panel, under the pooled reference (esfixedbaseperiod shrinks it to one period's mean: 0.024 vs 0.207 on the flagship). It is exactly zero for a time-invariant covariate on a balanced unweighted panel - where the margins column still reads `0bn.` with b = 0, so the `0bn.`/`0bno.` name is not a usable detector; the value is. Under `lattice()` with `contreatcontrols(basic)` it equals the baseline dose slope, always: the guard at ado ~1283 (`... & "latticepart2hash" == ""`) skips the ringer initialisation whenever a lattice is present and nothing else inserts a dose control, so plain `basic` with a lattice inserts NO baseline dose control on the default path (the author's own comment at ~1280 says it should).

**Mechanism 1 - `interactivecontrols()`, binary DiD. Flagship:** `use test/suite/data/dta_s_covars.dta; gen coh = cond(ttre==5,1,cond(ttre==9,2,3)); wooldid y coh t ttre, att cluster(i) fe(i) interactivecontrols(x1) esprelength(2) espostlength(3) jointtests` (cohorts of 50 units, unit FE, a time-varying covariate; no caution prints). The reference-cell margin is 0.2067 (se 0.078, t 2.65) and is invisible. What the user sees that is wrong:
- "p-value for joint test that all pre-treatment att horizon estimates are 0: 0.0510". The contrast set includes `_t==0`, so the test is "pre horizons = 0.2067"; the pre = 0 Wald on the same reported b/V is 0.7014 and the one-column-removed model gives 0.7307. The ticket's 0.146 vs 0.615 reproduces exactly on the ticket's own configuration. `pretrendpower()` on the same run prints a pre-trend p of 0.678 (the pre = 0 Wald) and the boottstat joint test also tests pre = 0, so one command can print joint pre-trend p-values on different nulls.
- Every displayed horizon, main att and pretreatment att are shifted by `s000 x E_w[x_dm | that cell]` - horizon-specific, not the anchor and not a constant: displayed ES rows (-0.047, -0.066, 1.296, 1.363, 1.232) versus (0.035, -0.042, 1.262, 1.277, 1.091) without the reference-cell column, shifts of -0.08 to +0.14 against standard errors of 0.08-0.12 (identity verified to 1.5e-15); standard errors move too (18-40 percent on the simulated panels).
- The reported numbers are not estimable functions of the model. The reference-cell slope column is exactly collinear with `i.t#c.x` plus the treated-cell slopes (modulo the absorbed effects), so the engine's collinearity drop decides them, and `s000` equals the covariate slope of whichever `t#c.x` column was dropped: merely reordering the reghdfe terms drops a treated-cell slope instead of `12.t#c.x1`, moves the flagship horizons by up to 0.10, moves the joint p from 0.051 to 0.639 and switches the multicollinearity caution on; reghdfe versus reg (same fit, same R-squared) differ in `e(b_es_att)` by up to 0.09 and in main att by 0.10 in the no-fe twin. The bite scales with the dropped period's covariate slope times the within-cohort trend of the control and can be large: on a simulated panel with a trending covariate (`~/.claude/jobs/be9644d0/tmp/refute/gen2.do`, 120 units, untreated-state covariate slope 0.3t, true pre-effects 0, true ATT 1.0-1.5) the current build reports pre rows -2.96/-2.10/-0.81, post rows 2.28/3.22, att 3.92 and joint p 1.9e-38 - a wholly spurious pre-trend and a 2.6x ATT - where the corrected construction gives ~0 pre rows, 1.41/1.42, 1.52 and p 0.91. `e(b_es_*)/e(V_es_*)` (HonestDiD, pretrends, `pretrendpower()`), the adversarial line test, `gteffects` and the plots all consume these values; under `bootstrap()` and `permute()` the anchor half disappears (their joint statistics use the pre rows only) but the shifted rows remain. The poisson/ppmlhdfe path carries the same artifact. `unconditionalse` happens to give the corrected numbers on these fixtures because reg dropped the reference-cell slope - an empirical property of reg's collinearity choice, not a guarantee - and with `fe()` present `unconditionalse` is not the same model anyway: the fe list is passed bare to reg (ado ~1466), i.e. a linear unit-id term, which is a separate defect.

**Mechanism 2 - `lattice()` + `contreatcontrols(basic)`. Fixture of record:** `test/suite/data/continuous_control_dense.dta`, `wooldid y_cont_common cohort t ttre, att contreat(dose_common) contreatcontrols(basic) lattice(baseTreated 2) esprelength(2) espostlength(2) robust jointtests safety(off)` reproduces the ticket's 1.0198 / 1.78e-3 exactly. Every ame row - main, pretreatment, each ES_ame horizon - equals the corrected value plus the baseline dose slope to machine precision: main:ame 1.267 vs 0.248, ES_ame pre rows 0.81 and 0.77 with intervals excluding zero versus -0.21 and -0.25 corrected; on test/data/dta_cont.dta (DGP base slope 2) the pre rows print 2.01 and 1.97 where the truth is 0. The att rows are untouched (1e-15). This IS a printed non-zero "reference effect" in substance, beside a plot reference planted at 0. `e(joint_Choriz)` is essentially unaffected (0.0036 vs 0.0036) only because the uniform shift cancels inside `contrast(overjoint)`; the ticket's "7.3e-44" is the pre = 0 Wald on the shifted ame rows (W = 213, df 1414), which is exactly the statistic the boottstat joint test computes, so bootstrapped ame joint tests under lattice+basic are wrong today. Cures measured: forcing the guard true, `unconditionalse`, `basic byTreated` under robust; `basic byTreated` under `cluster(i)` is NOT a cure on dta_cont because the all-zero-VCV fallback (ado ~1530) re-runs through reg, which drops the earlier-listed byTreated ringer columns and keeps the cell block's dose main effect (traced) - so the "later-listed collinear terms get dropped" rule the code comments rely on does not hold. The new `permute()` build inherits this leak: the ame permutation distribution is then not centred at zero, and the shift intervals are blanked there with a caution (the p-values stand).

**Practical bite, in order.** (1) lattice + basic: every ame row on the printed table is off by the baseline dose slope - the largest and most visible effect. (2) interactivecontrols: every horizon row, main and pretreatment att, their standard errors, `e(b_es_*)/e(V_es_*)`, gteffects, the Roth and adversarial diagnostics and the plots are solver-dependent whenever the covariate varies within cohort over time or the panel is weighted or unbalanced; sizes range from negligible to catastrophic depending on the covariate's trend. **Solutions.**

# Project Chunk: Improving the Assessment Suite

Let's review the suitability of our assessment suite. One thing I want to be careful with is that we are making appropriate use of pathological data. It's important that wooldid does not fail catastrophically when given pathological input data - defining 'fail catastrophically' as presenting wrong results that look plausibly correct. We want wooldid to either present true correct results, or fail in an observable way. So testing pathological data is useful. But it's also not always the most determintive for checking whether features work as intended when given useful data. So we should make sure that we have these difference cases marked, and should understand scenarios using pathological data as an input as mainly being about answering the question 'does wooldid and this or that feature of it handle the pathological data correctly', rather than as being about answering whether a given feature is functioning optimally (which we may wish to test in other settings). Of course, a perfect distinction can't be drawn between these cases, and edge case failures can reveal deeper errors - but we do need to make sure that we tend to test features using both pathological and non-pathological data. And when we find an error using pathological data, we should inform our diagnosis of the problem based on both that performance and how the feature performs using better behaved input as well. Combining both signal streams is not guaranteed to add value, but it is a good path to investigate. Please make a brief note of this general concept, and make relevant updates to the assessment suite as appropriate.
