tip (`4388ba5` at the time of writing). Scope: `wooldidinstall/wooldid.ado` and
`wooldidinstall/wooldid.sthlp`, read for defects — code that does not do what the help or the

## 0. Purpose and method

**Nine lenses.** Nine independent readers each swept one subsystem: the estimator core, the
aggregation and margins layer, analytic inference, the bootstrap engine, the permutation engine,
the cell collapse, display and replay, edge cases and input validation, and estimands/method.
Each read the code first and ran Stata only to confirm a suspected defect, under a hard cap of one
Stata process per reader.

**Reproduce-and-refute verification.** Every finding was handed to a verifier told to reproduce it
in Stata where a claim was numerical, and then to try to refute it on four fronts: is the behaviour
documented as intended; is there a guard the finder missed; is the finder's "should" itself wrong;
and is the item already covered by the 2026-09-05 review, the 2026-09-06 rulings, the consistency
sweep or the practice sweep. Verifiers were instructed to correct the finder rather than agree with
them, and several did: three findings were narrowed, four had their severity or kind changed, two
had their proposed fixes rejected as wrong, and one had its stated mechanism replaced.

### 2.1 Estimator core and specification

#### BS-1. `fe()` is categorical on the reghdfe path and continuous on the regress path

**Location.** `wooldid.ado:1575-1580` (the `regress`/`poisson` branch, which pastes the `fe` macro
bare into the varlist) against `1546-1571` (the reghdfe/ppmlhdfe `absorb()` branch); caution at
`4744-4747`; `syntax` declares `fe(varlist fv)` at `516`/`4680`.

**What the code does.** On the default path `fe()` goes into `absorb()`, where a bare varname is
categorical. Under `customvce()` or `unconditionalse` the same macro is pasted bare into `regress`,
where a bare varname is a single continuous regressor. The only signal is a caution saying the
options are "not compatible with absorbed fixed effects. You must specify anything in fe as
controls, manually specifying any needed i. prefixes" — but the option is still honoured, as a
linear term, and nothing afterwards says the substitution happened.

**What it should do.** sthlp:874 says the contents of `fe()` are "passed directly to reghdfe as
fixed effects (into its absorb statement) without modification. Variables given will be interpreted
as categorical variables." On the regress path they are not. A categorical fixed effect silently
degraded to a linear trend in the category codes is worse than dropping the option, which is what a
reader of "not compatible" would expect.

**Reproduction.** `test/data/dta_binary.dta`, `gen grp = mod(i+t,4)+1` (crossed with both `i` and
`t`): `att fe(grp)` gives att `.8441905`; `att customvce(robust) fe(grp)` gives `.8443958`;
`att customvce(robust) fe(i.grp)` gives `.8441905` — matching the reghdfe run — and
`att customvce(robust)` with no `fe()` gives `.8445031`. So the option is honoured (B differs from
the no-`fe()` run) and is honoured wrongly (B differs from A and from C).

**Verifier: confirmed.** Two refinements. "Silently" overstates it — the caution does print, on
both runs, ungated by `safety()`; the defect is that it mis-describes what the code then does. And
the scope is `fe()` only: `ccc_absorb()` is built at `1309` as an explicit `c.` term, which means
the same thing in `absorb()` and in a varlist. Line `1644`'s second `reg` refit is unreachable with
a non-empty `fe()`. Not a duplicate of F060, which is about the fastcollapse eligibility gate.

**Fix.** In the regress/poisson branch, normalise once before use:

```
local feinj
foreach fetok of local fe {
    if strpos("`fetok'", ".") == 0 & strpos("`fetok'", "#") == 0  local feinj `feinj' i.`fetok'
    else                                                          local feinj `feinj' `fetok'
}
```

and inject `feinj` at `1579-1580`. Leave the reghdfe branch untouched. Rewrite the caution at
`4744-4747` to say the `fe()` terms are entered as categorical regressors rather than absorbed —
numerically equivalent, slower, and consuming reported degrees of freedom — and drop the
`ccc_absorb()` half, which is unaffected. Test: assert `reldif(att_B, att_A) < 1e-6` and
`reldif(att_B, att_C) < 1e-6` while `reldif(att_B, att_E) > 1e-4`, plus the poisson twin.

#### BS-2. The forced-reference-period caution is gated off at `esprelength(1)`

**Location.** `wooldid.ado:803` and its timetrends twin at `823`:
`if "`safety'" == "off" | `esprelength' <= 1 {` — the fast branch, which does the replace silently;
the `else` branch holds the `assert` and the caution.

**What the code does.** Every unit's first in-sample period (first two under `timetrends`) is folded
into the reference pool. When that row is also a requested horizon the program is supposed to warn.
The gate skips the check whenever `esprelength <= 1`, so at `esprelength(1)` — where relative period
-1 is a requested horizon — a unit whose only pre-period is `ttre-1` silently drops out of that
horizon while keeping all its post cells, and the pre-horizon is estimated on a different set of
units from the post horizons.

**What it should do.** The gate should be `esprelength == 0`. At 0 nothing is requested and the
assert is provably vacuous (the unit-level nopre drop at `772-775` removes every unit with
`ttre <= mint`, so `_t < 0` there and the window replace has already blanked those rows), so the
change adds no message at 0 and the correct message at 1. sthlp:683 documents the forcing itself
with no `esprelength(1)` carve-out, and nothing in code or help records an intent to exempt 1.

**Reproduction.** 12 units x 6 periods, `ttre = 4` for `i >= 5`, units 9-12 truncated to `t >= 3`
so their only pre-period is relative period -1. `esprelength(0)`: no caution (correct),
`e(escomp_refN) = 16`. `esprelength(1)`: **no caution**, `refN = 12`, and `e(escomp)` shows
`pre1 nunits = 4` of 8 treated units. `esprelength(2)`: the caution prints on the identical four
forced rows, `refN = 8`. The timetrends twin behaves the same way with the truncation at `t >= 2`.

**Verifier: confirmed, both branches.** Severity medium: the `pre1` number is what the pooled-
reference design produces; what is wrong is that its changed composition is announced at
`esprelength >= 2` and concealed at 1, the value at which a user is least likely to suspect it.

**Fix.** `803` and `823`: `<= 1` becomes `== 0`. Guard the tail advice, which is degenerate at 1:
`if `esprelength' > 1 dis as text "(Or request estimates for fewer pre-treatment horizons.)"`, and
split the timetrends copy at `833` so `esprelength(1)` prints only the drop-timetrends line. Test:
the panel above must produce the caution at `esprelength(1)` on both branches, must not produce it
at `esprelength(0)` or on an untruncated panel, and `e(b)`/`e(V)` must be bit-unchanged (both `_t`
paths are identical, so this restores a warning, not a result).

#### BS-3. `interactivecontrols()` is inert whenever cohort-by-period cells hold one observation

**Location.** `wooldid.ado:1305-1329` (the demean at `1313`, the `interinject` term at `1329`); the
generic collinearity caution at `1841-1852`; the analogous contreat screen (SI-A4/R6) at
`1855-1868`.

**What the code does.** The treatment-effect half of the option is the demeaned covariate
interacted with the cohort-by-period cell dummies. When `i` is the panel unit and the data have one
row per unit-period — the modal setup, and the layout the help itself recommends at sthlp:62-64 —
each treated cell holds one observation, so every cell-slope column is a scalar multiple of its cell
dummy and is dropped. The run then reports "Note: the multicollinearity caution above was triggered
375 times total" and a point estimate that differs from the no-controls run only through the
surviving `i.t#c.x` term.

**What it should do.** The help promises "treatment effects are permitted to vary linearly with the
de-meaned variables" and that the specification "most closely mimics the approach to including
covariates that appears in Wooldridge (2025)". Under fine `i` neither is delivered. The parallel
requirement for contreat's within-cell dose slopes *is* documented (sthlp:156-160) and detected at
run time by the R6 screen; `interactivecontrols()` has neither.

**Reproduction and the verifier's corrections.** Confirmed, with the scope both widened and
narrowed. Widened: a *time-varying* covariate is dropped just as completely — on
`test/data/dta_binary.dta` with a random `xtv`, `interactivecontrols(xtv)` and
`controls(i.t#c.xtv)` return att `.82495119` and se `.0756637` and every other table cell
bit-identically, so under fine `i` the option reduces exactly to `controls()` for any covariate, not
only a unit-invariant one. Narrowed: the finder's headline "a unit-level covariate cannot qualify"
is false in general — with a coarse `i` (one group per onset) a unit-level covariate is live
(att `.81252878` vs `.82038504` for the controls-only twin) and no caution fires. So the precondition
is within-cell variation, not time-variation, and it is a property of the user's `i`.

**Verifier: confirmed**, kind changed from `econometric` to `bug`: no reported number is wrong; the
defects are a missing detection screen and an undocumented precondition. The generic caution is
also misleading in both directions here — the att *is* identified (it equals the controls-only fit),
and what is not identified is exactly the thing the user asked for, which the message never names.

**Fix.** Add the `interactivecontrols` twin of the R6 screen after the collinearity count at
`~1863`, keyed on `interlist` (the demeaned copies, built in order at `1310-1318`, so word position
maps back to the user's variable names): when every treated cell slope for a control is omitted and
none survives, name the variable, say the treatment effects do not vary with it, and say the run is
identical to `controls(i.t#c.x)`. Suppress or soften the generic caution when the named one fires.
Help: one sentence in the `interactivecontrols()` entry mirroring sthlp:156-160. Test: assert the
named caution fires and that att and se equal the `controls(i.t#c.xtv)` run to 1e-10 under fine `i`;
assert no caution and a different att under coarse `i`; and a third leg with a unit-invariant
covariate under coarse `i`, to guard against a fix keyed on time-invariance rather than on
within-cell variation.

#### BS-4. A ppmlhdfe separation is reported as a multicollinearity failure

**Location.** `wooldid.ado:1547` (the `qui cap ppmlhdfe` call) and `1770-1840` (the dropped-treated-
dummy screen, `error 322`); the unconditional `contreatwithin` advice at `1830`; the code's own note
that estimators drop rows after the screens at `1658-1660`.

**What the code does.** Under `poisson`, a treated cohort-period cell whose outcome is zero on every
row is separated: ppmlhdfe drops those observations and marks the coefficient omitted. wooldid's
screen counts surviving rows on `ifstatement` rather than `esamp`, sees the `o.` marker, and exits
`r(322)` with "a treated cohort-period dummy coefficient was dropped for multicollinearity",
followed by advice to "specify contreatwithin if you have a continuous treatment intensity
variable" — on a call with no `contreat()`. Under `safety(off)` the run completes with those rows
gone and the cell absent from the ATT.

**What it should do.** An all-zero treated cell under poisson is a separation, not a collinear
dummy, and the rows are in `ifstatement` but not in `esamp` — the exact discriminator. The refusal
itself is defensible; the diagnosis and the remedy are not.

**Reproduction.** `test/data/dta_binary.dta`: baseline `att poisson` gives rc 0, N 960,
att `.12400474`. After `replace ycount = 0 if i == 1 & t >= ttre & ttre < .` (7 rows) the same call
gives `r(322)` with the multicollinearity text and the `contreatwithin` line; under `safety(off)` it
gives rc 0, N 953, att `.12255701`. A direct engine call on the doctored data,
`ppmlhdfe ycount ib0.cellid, absorb(i.i i.t)`, prints "(simplex method dropped 7 separated
observations)" and then its own "omitted because of collinearity" note — which is why wooldid
cannot simply forward the engine's text.

**Verifier: confirmed**, with the trigger frequency raised. Because `i` is the panel unit here, a
treated cell is a *single* observation, so one zero count in any treated unit-period fires the
refusal; on genuine count data with `poisson` that is close to certain rather than an edge case.
Two corrections: `safety(off)` is not fully silent (the header prints "7 obs dropped"), and the
`contreatwithin` sentence is conditional in wording but emitted unconditionally in code, which is a
separate one-line gate defect. `test/suite/configs.csv:34` (`trig_pois_sep`) already pins `rc 322`
for a separation shape, so the return code is known to the battery; only the message is wrong.

**Fix.** At `1820`, add a second count on `esamp`. When `poisson` is in force, that count is zero
and the cell's outcome is zero on every `ifstatement` row, take a separation branch: keep
`error 322` (so `trig_pois_sep` stays valid), name perfect separation and the offending
`(i, relative-t)` cells, say ppmlhdfe dropped those observations so the cell cannot contribute, and
give the real remedies (coarsen `i`, drop the cohort, or `safety(off)` to proceed with the cells
excluded). Add an always-on caution outside the safety gate reporting how many treated cells were
excluded by separation. Independently, wrap the `contreatwithin` line at `1830` in
`if "`contreat'" != ""`. Tests: separation message present and "multicollinearity"/"contreatwithin"
absent; the `safety(off)` twin at N 953 / att `.12255701` with the new caution; and a negative
control on an existing genuine dropped-dummy config, which must still say multicollinearity.

### 2.2 Aggregation and margins

#### BS-5. `impvalues` intervals are hard-coded at 95% while `level()` renames the columns

Found independently by the aggregation, inference and method lenses; three verifiers reproduced it
on two fixtures. **High, bug.**

**Location.** Six Ibragimov-Muller sites in `wooldid_worker`, each writing
`local im_ll = `b' + invt(r(df_t),.025)*`se'` / `im_ul = `b' - invt(r(df_t),.025)*`se'`:
`2329-2330`, `2378-2379`, `2491-2492` (binary pooled post, pooled pre, per-horizon) and
`2589-2590`, `2642-2643`, `2969-2970` (the contreat twins). Column names built at `3859-3860`,
`3986-3987`, `4029-4030` from `wdlvltxt` (`540`); `wdlvl` set at `539`; `ereturn scalar level` at
`4564`; the F054 `set level` plumbing at `535-538`.

**What the code does.** Under `impvalues` the analytic margins variance is switched off
(`local marginsdof nose`, `2281`) and the reported interval is built by hand from `ttest`'s `r(se)`
and `r(df_t)` with the tail probability written as the literal `.025`. F054 (`a969126`) made
`level()` reach the analytic tables by `set level` for the duration of the call; these six sites
never read `c(level)` or `wdlvl`, so they were not covered. The columns are nevertheless renamed
`lb_90ci`/`ub_90ci` and `e(level)` is posted as 90.

**What it should do.** sthlp:489: `level()` is "the confidence level for every reported confidence
interval — the analytic tables, ... The interval columns are labelled lb_#ci / ub_#ci for the level
in force ... and that level is stored in e(level)." The impvalues entry (sthlp:252-256) grants no
exemption, and nothing in the method fixes the level: wooldid does not use Ibragimov-Muller's
tabulated 5% critical values, it runs a plain `ttest` on the per-cluster estimates, whose interval
is level-parameterisable. `wooldid_gtx` (`10836-10840`) and `wooldid_ptp` (`9314-9315`) already do
this correctly.

**Reproduction.** `test/data/dta_binary.dta` (80 units, 50 ever-treated, IM df 49),
`att cluster(i) impvalues esprelength(2) espostlength(2)` at the default and at `level(90)`:
`e(wdidmainresults)` is bit-identical in every cell of all six rows (`mreldif = 0`), while the
colnames flip to `lb_90ci`/`ub_90ci` and `e(level)` to 90. `main:att` b `.74506742`, se
`.06462869`, interval `[.61519121, .87494362]` at both levels; half-width / se = `2.009575` =
`invttail(49,.025)` exactly. The correct 90% bounds are `[.63671413, .85342071]`. A third run at
`level(99)` is also bit-identical — there the reported interval is about 33% too narrow
(`2.0096` against `invttail(49,.005) = 2.6800`), which is anti-conservative in precisely the
small-cluster setting `impvalues` exists for. The non-`impvalues` control does move
(`mreldif = .0247`), isolating the hand-built branch.

**Verifier: confirmed** by all three. No documented carve-out, no guard (`wooldid_validate` checks
only the 10-99.99 range, and `6057` says "level() applies to every run"), and not a duplicate of
CS-2 (a different defect, an *unspecified* level resolving to a literal 95 inside the engine
rewirings) or of CS-105. The IM `t` and `p` come from `ttest` and are level-free and correct; only
columns 5-6 are wrong, and anything reading them — the ES plot, `saveplots`' `_ES.dta`, `esttab` —
inherits a 95% interval under a 90% label. Coverage gap that let it through: `test/test_level.do`
L1-L9 never exercises `impvalues`.

#### BS-12. The primary adversarial line test drops the reference-period normalisation

**Location.** `wooldid.ado:11331-11375` (`wooldid_advW`, the `alt==0` branch), called from
`wooldid_advx` and `wooldid_advstat` at `10219`; the in-code justification at `11313-11316`;
contrast the `alt==1` branch, which plants the reference row, and `wooldid_ptp`'s pre-trend fit at
`9404`/`9451-9453`, which does impose the normalisation.

**What the code does.** For the primary (non-`altmethod`) test the statistic is
`min over free (g0,g1) of (b - Xg)' V^+ (b - Xg)` with `X = [1, relyr]` on the estimated horizons
only and `q = rank(V) - 2`. The planted zero-variance reference row is used for the *display* OLS
line but never enters the test, on the stated ground that it "receive[s] zero weight under V^+ and
so [is] mathematically inert".

**What it should do.** Under `esfixedbaseperiod`, `b_h = theta_h - theta_r`, so any linear
underlying path implies `b_h = c*(h - r)`: a **one**-parameter family, a line through
`(esrel, 0)`, with `q = rank(V) - 1`. Because the constant vector lies in the column space of
`X = [1, relyr]`, the shipped statistic is exactly invariant to adding a constant to every
coefficient — so it has *zero* power against a uniform level shift of the estimated path, which is
the signature of an anomalous or anticipatory reference period, and one df less power against
everything else violating `g0 + g1*esrel = 0`.

**Reproduction.** Mata, `b=(1\1\1\1)`, `rel=(-3\-2\0\1)`, `V=.01*I`, `esrel=-1`:
`wooldid_advW(..., alt=0)` returns `W = 3.16e-29`, `q = 2`, `p = 1.000000` for a path that, with the
reference zero included, is visibly not a line. Carrying the reference row at a token variance
`1e-10` gives `W = 399.999984`, `q = 3`; the exact constrained statistic
`b'V^-1 b - (m'V^-1 b)^2/(m'V^-1 m)` with `m = rel - esrel` is `400`. So the shipped statistic is
**not the limit** of the corresponding non-degenerate problem — the code comment's equivalence is
false, because an exactly-known component is a hard restriction, not a zero-weight observation. On a
full run — 600 units, three staggered cohorts plus never-treated, no treatment effect at any
horizon, and a `+5` anomaly at the reference period only — every event-study coefficient comes back
at about `-4.99` with `t` between -110 and -140; wooldid prints joint pre-trend `p = 0.0000` and
**adversarial `p = 0.9432`**, while the through-the-reference statistic on the same
`e(b_es_att)`/`e(V_es_att)` gives `W = 29069.83`, `q = 5`, `p = 0`.

**Verifier: confirmed**, with **severity raised from medium to high** and one framing correction.
The behaviour is *documented*: sthlp:591 says "all estimated relative time period-specific effects
... some line, with slope and intercept unknown", sthlp:592-594 defines the df as
`rank(V) - 2`, and both sthlp:1118 and the printed labels at `9827`/`9969` say "(non-reference)".
So the finder's "silently drops" overstates it and this is not a code-vs-help contradiction — the
defect is that the documented null is the wrong null for a fixed-base-period event study. The
strongest internal argument is that wooldid's own pre-trend machinery already imposes the
restriction (`wooldid_ptp` fits with no intercept through the reference period, and sthlp:625 says
so), so the package carries two linear-pre-trend objects under two different normalisations.

**The two readings, for the author.** (a) *Fix the null.* Replace the design with
`X = rel :- esrel`; `q` becomes `rank(V) - 1` automatically, and the statistic equals the
constrained minimum distance (verified: 400, matching the `eps -> 0` limit). This is what the
estimator's own normalisation implies and what `wooldid_ptp` already does. (b) *Keep it.* The
shipped test is level-valid for the weaker null it labels, so this is lost power and a mislabelled
question rather than a size failure; a reviewer may prefer to keep the two-parameter null and only
sharpen the help and the printed label. Note the cost of (b): the headline diagnostic prints 0.9432
on a design whose intended null is violated at `t = -137`.

**Fix, if (a).** Two lines in the `alt==0` branch (`11356-11375`) plus a `timetrends` guard: with two
planted reference rows the constrained null collapses to `b = 0`, so set `W = z'z`, `q = k1` and
skip the `svsolve` rather than handing it an empty matrix. Leave `alt==1` and the display line
alone; both are documented as they stand. Text to follow: sthlp:591-595, sthlp:1118, `9827`/`9969`
(drop "(non-reference)"), the false comment at `11313-11316`, and the "no testable residual
dimensions" comment at `10251-10253` (two horizons become testable at `q = 1`). Downstream:
`wooldid_advW` `alt==0` is also the statistic for `boottstat` (`12311`, `12360`), the fixed-metric
bootstrap rank test (`13437`, `13442`) and `permute()` (`7886`); recentring stays valid, but every
adversarial p in every baseline moves, so this needs a battery re-bless under the pristine-twice

the closed-form constrained value; the end-to-end DGP above (adversarial p must go from `.9432` to
~0 while the joint p stays 0); and a null-size check on the same DGP without the spike.

#### BS-13. `customvce()` and `unconditionalse` change the cluster-robust small-sample correction

**Location.** `wooldid.ado:1542-1573` (the reghdfe/ppmlhdfe branch) against the `reg`/`poisson`

discriminating legs pin the mechanism: `robust` vs `customvce(robust)` agree to eight digits

closes — the robust run's `e(df_r) = 494` gives `K_reg = 466`, hence `K_hdfe = 387`, and

**Verifier: confirmed** for the linear path, with three corrections. The `customvce` path is

**The two readings, for the author.** reghdfe's nested-FE rule is the standard one (Cameron-Miller

agree — rescale the posted `e(V)` on the reg branch by `(N-K_reg)/(N-K_reg+L)` where `L` counts the

the file already computes the nesting predicate twice, at the `jointtests` screen (`1509-1531`) and
in the AMESE R1 block (`1600-1620`); hoist that parse into a helper and reuse it. Either way, add

message, so a rescued run says which convention its recovered SEs are on. Test: assert `b` equal to

### 2.8 Edge cases and input validation

#### BS-33. No treated unit at relative period 0 crashes a bare `wooldid y i t ttre, att`

**Location.** `wooldid.ado:874` (`local min_t = abs(r(min))`), `893` (`local espre = `min_t'`),
`1755-1763` (the horizon scan and `matrix `relyrcolumn' = (`relyrlist')'`); the pre-treatment margins
at `2343`.

**What the code does.** In the pooled-reference branch `_t` is set missing for every relative period
below `-esprelength`, so with the default `esprelength(0)` the surviving `_t` are all `>= 0` and
`r(min) >= 0`. `abs(r(min))` then returns a **positive** `min_t` whenever no treated unit is in
sample at exactly `t == ttre`, and `espre = min_t` invents pre-treatment horizons that do not exist.
Two crashes follow: a bare `att` call runs the horizon scan, matches nothing, and aborts with a bare
`r(198)` "invalid syntax" from `matrix `relyrcolumn' = ()'`; with `espostlength(#) > 0` some horizon
matches and the run reaches the pre-treatment margins call whose subpop is empty, dying `r(461)` "no
observations in subpop() subpopulation".

**Reproduction.** Two ordinary, help-blessed shapes. (A) 12 units x 6 periods, `ttre = 4` for
`i <= 4`, `drop if i<=4 & t==4` (the implementation year dropped for treated cohorts — standard
practice): bare `att` -> `r(198)`; `att espostlength(2)` -> `r(461)`;
`att esprelength(1) espostlength(2)` -> rc 0, because relative period -1 survives. Without the
dropped row the same panel runs rc 0, so the gap alone is the trigger. (B) a biennial panel
`t = 1,3,...,11` with onset 6, so relative periods are `-5,-3,-1,1,3,5` and 0 is never realized:
bare `att` -> `r(198)`; `espostlength(2)` -> `r(461)`. sthlp:65-66 explicitly blesses both shapes
("gaps are all fine"; "integer spacing is not required: biennial or five-year panels are fine").
`safety(off)` is not an escape. The `esfixedbaseperiod` twin at `976` is inert, since the
reference-period screen drops any cohort lacking the reference row first.

**Verifier: confirmed**, and the finder's fix was tested rather than only proposed. On a patched copy
with `local min_t = max(0, -r(min))` all four crashes clear and the DGP effect is recovered exactly
(`att = 1.5` on both panels), while `dta_binary` with `att cluster(i) esprelength(2) espostlength(2)`
is unmoved (`att .8235285`, se `.0629643`) — as it must be, since `abs(x) == max(0,-x)` for every
`x <= 0` and `r(min) <= 0` is the normal case. The finder's second fix is independently **necessary**,
proved: under the `min_t` patch alone, panel B with `espostlength(1)` still dies `r(198)`, because
the only scanned horizon is relative period 0, which that panel never realizes, so `relyrlist` is
still empty. One characterisation the finder omitted, which bounds the item: an inflated `min_t`
implies zero surviving pre rows by definition, and the relyr recovery `relyr = horiz - min_t - 1` is

identity, so all stay mutually consistent. Do **not** touch the inert twin at `976`. (ii) `1763`:
before building the matrix, guard `if "`relyrlist'" == ""` with an informative `error 459` naming the
requested window and the relative periods actually realized, e.g. "requested relative periods 0..1,
realized -5 -3 -1 1 3 5 (the onset period is not observed for any treated cohort — check for an
onset-year gap or an onset off the panel's time grid)". Whether to soften that to a caution-and-skip
(drop the ES block, report `att` only) is the author's call. Nothing changes in the engine shells,
which read the corrected value via `e(wdid_espre)`. Tests: both panels at bare `att` and
`espostlength(2)` -> rc 0 with `att == 1.5`; panel B `espostlength(1)` -> the new informative error,
explicitly not a bare `r(198)`; and a regression pin on `dta_binary` (`.8235285`, `.0629643`, relyrs
-2 -1 0 1) byte-identical before and after.

#### BS-34. Float-stored `t`/`ttre` above 2^24 silently merge periods and cohorts

**Location.** `wooldid_validate`, the raw-data screens at `wooldid.ado:5013-5030` (`i` integrality and
positivity, poisson `y >= 0`) and the `t - ttre` grid screen at `5327-5350`; no storage-type or
magnitude screen exists anywhere (`grep` for `recast|16777216|: type` returns only the F13 error text
at `720`, an unrelated control-variable check at `5629-5630`, and a comment at `1269`).

**What the code does.** Float cannot represent consecutive integers above `2^24 = 16,777,216`; the
ULP in `[2^24, 2^25)` is 2. An 8-digit date variable created the ordinary way (`gen t = 20150000 +
...`, float by default) is rounded before wooldid sees it, so consecutive calendar periods merge
pairwise, the `(i,t)` cell structure is wrong, and the run completes rc 0 with no message. Every
existing screen passes on the rounded data: `i` is a clean double, `20150004 - 20150002 = 2` is an
integer, and `ttre` is constant within each `i`.

**Reproduction.** A 20-period panel, 12 units, onset at `t0 = 8`, built as `20150000 + t0`:
**float** gives rc 0, `att = 1.3928571`, se `.0800771`, `t = 17.39`, `p = 4.4e-40`, CI
`[1.2348, 1.5509]`, R2-within `.5264`, and **zero cautions** — a clean, complete, wrong table. The
double-stored twin gives `att = 1.5` exactly with R2-within 1. Both numbers are what the merge
predicts (cell effect `0.75` in the half-treated onset cell, `1.5` elsewhere:
`(0.75 + 6*1.5)/7 = 1.392857`), so wooldid is computing correctly on rounded inputs and the defect is
purely the absence of detection.

**Verifier: confirmed**, with three corrections. The finder's own 6-period sketch does not reproduce
their numbers — it gives `att = 1.125` and R2-within `.29833`, and it is *not* silent (it emits an
all-zero-VCV caution for an unrelated small-design reason); the 20-period panel above is the
canonical repro and the genuinely silent case. And the finder's remedy is wrong: `recast double x`
on an already-float variable widens storage while preserving the rounded values exactly and recovers
nothing — the only remedy is regenerating the variable as double from its source, which is what
sthlp:66 actually says. That sthlp line documents the hazard verbatim ("8-digit calendar dates
exceed float precision, so a float-stored onset variable is rounded before wooldid sees it, silently
merging adjacent cohorts") and `720` names it inside the F13 error text — so the behaviour is known.
What makes it a defect rather than a documented limitation is that every analogous input hazard is
screened with exactly this kind of two-line check, and this one, with a two-line detector, is not.
No float or precision item appears in any of the four 09-05/09-06 records.

**Fix.** In `wooldid_validate`, after the `i` integrality screen and gated on `safety() != off`, for
each of `i`, `t` and the as-given `ttre`: if the storage type is float and the in-sample maximum
absolute value exceeds 16,777,216, print a caution naming the variable and saying the values were
rounded before wooldid saw them, which can merge adjacent periods, cohorts or IDs with no other
symptom, and that an 8-digit calendar code or a `%tc` datetime must be **regenerated** as double
from its source (recasting does not recover the lost values). Caution rather than error: float codes
above `2^24` that are legitimately even or coarse are exactly representable, so a hard error would
have false positives, and because the rounding happened upstream no exact detector is possible —
type plus magnitude is the only available signal. Bundle the one-line text fix at `720`, which
currently advises the ineffective `recast double`. Test: the 20-period panel above, asserting the
caution fires on the float run (today rc 0 with `att = 1.3928571` and no message), does not fire on
the double run (`att = 1.5`) or on a float `t` below the threshold, and is suppressed by
`safety(off)`.

**Observed en route, out of scope.** On the 6-period design the all-zero-VCV caution blames
"continuous treatment effect estimation coupled with use of analytic clustered SEs" on a binary,
robust-SE run — see BS-35, which files the same wording defect.

the caution text in `wooldid_amescreen` `mode(vzero)`, called at `1632` with no `contreat` gate, text

#### BS-36. `esprelength()`/`espostlength()` count integer slots, so gapped panels lose realized horizons

**Location.** `wooldid.ado:874-893` (`min_t`, `max_t`, `local espl = min(`max_t',`espostlength')`,
`local espre = `min_t'`), `1750-1752` (`horizonend = horizonstarter + espre + espl - 1`),
`1755-1763` (only horizons present in `e(b)`'s colnames are kept).

**What the code does.** The reported window is one contiguous integer block of relative-period codes.
Codes inside the block with no cells are dropped silently, and realized horizons outside the block
are never reached — every empty slot inside the block eats one horizon off the far end. Because
`_t = t - ttre` preserves gaps in the relative-period axis as gaps in the horizon codes, a biennial
or off-grid panel has half its window empty by construction.

**Reproduction.** All from one run. (A) control, annual `t = 1..6`, onset 4, `esprelength(2)
espostlength(3)`: colnames `pre2 pre1 post0 post1 post2` — as requested. (B) biennial
`t = 1,3,...,11`, on-grid onset 7, same request: `pre2 post0 post2` — one of two pre horizons and two
of three post. Relative period 4 (`t = 11`) is a treated dummy in the fitted model, is in `e(b)`, and
enters the reported `att` (whose margins subpop is unrestricted above), but is absent from the ES
table. (C) biennial with an off-grid onset 6: `pre1 post1` only. (D) the same data as B at
`esprelength(4) espostlength(6)`: `pre4 pre2 post0 post2 post4` — doubling the request recovers all
five realized horizons, which pins the integer-slot mechanism. (E) an annual panel with calendar
period 4 absent, so relative period 0 has no cells: `esprelength(1) espostlength(2)` gives
`pre1 post1` and omits the realized relative period 2. sthlp:65-66 blesses gapped and biennial
panels; sthlp:574-578 describes the options as "the number of ... relative time period-specific
effects to be estimated".

**Verifier: confirmed**, and **distinguished from PS-61**. In case B the `min()` in
`espl = min(max_t, espostlength)` does *not* bite (`max_t = 5`, `espostlength = 3`) and the data do
support three post horizons, yet only two are reported — so PS-61's proposed caution, keyed on the
integer range, would stay silent on every case here; this needs a realized-count diagnostic instead.
The code's own comment at `1021-1022` ("non-fixed base will always present all horizons flagged by
`_t`, since it only generates flags if they will be used") is falsified by case B. No guard: the only
horizon-dropping caution (`3168`) fires only for subgroups when margins reports an omitted term, and
`gteffects`' `inwindow` column exposes it only if the user asks for `gteffects`.

**The two sides must be split.** *espostlength* is a pure display/window defect, cleanly fixable in
both reference regimes: realized post horizons above `horizonend` stay in the model and in `att` but
are unreported. *esprelength under the pooled reference* is different — the integer threshold there
also decides the reference pool, and that is documented (sthlp:1091: the reference pool is "treated
rows earlier than the requested pre-window (relyr < -esprelength)"), so changing the pre count moves
rows between the reference pool and the estimated set, i.e. an estimator change. The finder's blanket
"count realized horizons when resolving espre/espl" is therefore too broad on the pre side, which is
a help inconsistency and an author ruling rather than a code fix. Under `esfixedbaseperiod` the pre
side is display-only and worse: a biennial panel with `esrelativeto(-2) esprelength(2)
espostlength(3)` returns `post0 post2` and **no** pre rows, while the same table prints a
`pretreatment att` row of `-1.78e-15` (`t = -1.27`, `p = .21`) aggregated over realized relative
periods -4 and -6 whose codes sit outside the window — a pre-treatment average with none of its
components visible (see also BS-7).

**Fix.** Resolve the window on realized horizon codes at the setup site (`~1033`, after `_t` is final
and shifted) rather than at the harvest loop, since every downstream consumer reads
`horizonstarter`/`horizonend`: `glevelsof `_t' if `_t' > 0` for the realized codes, set
`horizonend` to the `min(espostlength, #realized codes at or above the onset code)`-th realized code,
and under `esfixedbaseperiod` set `horizonstarter` to the `espre`-th realized code counting back from
the reference. On gap-free panels the codes are consecutive and both reduce provably to the current
arithmetic, so no blessed baseline moves. Leave the pooled-regime pre threshold at `800` alone. Add
a caution at the harvest site and its contreat/subgroup twins, keyed on the **realized count** and
not on `min(max_t, espostlength)`, naming the requested relative periods with no cells and any
realized periods outside the window. Help: say the window is counted in units of `t`, not in observed
panel periods, and cross-reference sthlp:66. Tests: the biennial fixture asserting
`pre2 post0 post2 post4` after the post-side fix (not `pre4 pre2 ...`, since relative period -4 stays
pooled by the documented pre rule); the hole fixture asserting `post2` is included; a contiguous
regression pin; and an `esfixedbaseperiod` leg asserting the ES pre panel is non-empty whenever the
`pretreatment att` row prints.

#### BS-37. The if-qualifier selects `exp == 1`, not Stata's `exp != 0`

**Location.** `wooldid.ado:617` (`qui gen `ifvar' = `if''), `655`
(`local ifstatement `ifvar' == 1`), `625-626` (`local dropcount ((`if') == 1)`), `1594` (the
dropped-observation count); the deliberate rationale at `5013-5019`; the same `((`ifr') == 1)` form
at `5878`, `6251`, `6267`, `7105`, `8171`.

**What the code does.** `syntax [if/]` strips the keyword, so the raw expression's *value* is stored
and rows are kept where it equals exactly 1. Every other Stata estimation command keeps rows where
the expression is non-zero.

**Reproduction.** A 72-observation, 12-unit panel with 6 treated units.
`reg y i.i i.t if flag` (flag in {1,2}) gives `e(N) = 72`. (A) with `flag == 2` on all six treated
units, `wooldid y i t ttre if flag, att robust` gives `r(459)`, "cannot find either a treated time
period for any treated units..." — a message about the panel, not about the `if` expression. (B) the
stronger case, with `flag == 2` on only two *control* units: rc 0, `N = 60`, `att = 1.49048`, and the
header prints "N = 60 (0 obs dropped from initial sample)" with no caution — while `if flag != 0` on
the same data gives `N = 72` and `att = 1.48686`. Twelve rows vanish silently, the run looks clean,
and the number differs.

**Verifier: confirmed**, and the dropped-observation misreport is real: `dropcount` uses the same
`== 1` form, so `count if `dropcount' & e(sample)==0` cannot see the rows the rule removed, while
sthlp:1128 defines `e(N_dropped)` as the "number of observations dropped from initially specified
sample" — a user who typed `if flag` specified 72 rows, got 60, and was told 0 were dropped. The
convention is internally consistent: every downstream consumer of the forwarded expression uses the
same rule, so the estimation sample, the permutation design count and the bootstrap frame agree.

**The two readings, for the author.** (a) *Keep it.* The comment at `5013-5019` shows the choice is
deliberate and explicitly considers "bare flag variables with nonzero or missing values, which a
plain if-qualifier would wrongly include" — the `== 1` rule does dodge Stata's missing-is-truthy
footgun. Then the silence is the defect: add a count-and-caution when the expression is non-zero
somewhere but not exactly 1, fold that count into the dropped-observation line, and state the rule in
the general sample-formation text (today it appears only inside the `permute()` entry, sthlp:400).
(b) *Adopt Stata's rule* (`!= 0 & !missing(...)`) — but then at all six sites at once, since the
present agreement across the estimation sample, the permutation design and the bootstrap frame is
the one thing this behaviour gets right, and it would change the documented `permute()` semantics.
Severity medium: a bare non-0/1 variable as the `if` expression is uncommon (most `if` expressions
are comparisons yielding 0/1), but when it fires the output is a clean-looking wrong number.

**Fix, under (a).** After `617`, count `ifvar != 0 & ifvar != 1 & ifvar < .`; when positive, caution
with the count, state the exact-1 rule, and suggest `!= 0` if standard behaviour is wanted. Fold the
count into `droppedobs` (or post `e(N_ifexcluded)` and name it in the header) so the header stops
contradicting sthlp:1128. Add one sentence under the syntax diagram at sthlp:56 cross-referencing
sthlp:400. Test: the case-B panel asserting the caution prints, the count is accounted for, and
`if flag != 0` gives `N = 72`.

### 2.9 Estimands and method

#### BS-38. `e(gteffects)` under `interactivecontrols()` reports covariate-zero cell intercepts

**Location.** `wooldid.ado:1929-1950` (the harvest) and the Mata assembler `wooldid_gtx` at
`10797-10871`; the regressor built at `1329`; the analogous refusal for `contreat()` at `4795-4796`;
the help's claims at sthlp:953-954, 957-961, 964-965 and 968-970.

**What the code does.** `gteffects` reads the raw stage-1 coefficients matching
`<g>._i#<h>._t#1.targetflag` and reports them as the cohort-by-relative-period effects. With
`interactivecontrols()` the model also carries `i._i#i._t#1.targetflag#c.(x - xbar)`, so the cell's
actual treatment effect is `beta_it + delta_it * mean(x - xbar | cell)` while `e(gteffects)` reports
`beta_it` alone — the effect at the cohort's grand covariate mean. The divergence is invisible on
one-observation-per-cell panels, where the slope columns are collinear with the cell dummies and
drop, so it needs coarse cohorts to see.

**Reproduction.** 8 cohorts x 25 units x 8 periods, cohort-correlated covariate, checked with the
table's own weight columns rather than a simple mean. (A) time-varying `interactivecontrols(x)`:
`att`/`att_it` aggregate `1.9484102645` against a weighted mean of cells `1.9443340970` (gap
`4.08e-03`); `att_i`/`att_itime` `1.9679249582` against `1.9610888393` (gap `6.84e-03`). (B) the
same model with no `interactivecontrols`: gap `0.000e+00` on all four. (C) time-constant control on
a balanced panel: `0.000e+00`. The mechanism was then pinned exactly: the `beta` parsed from `e(b)`
equals the gteffects estimate column to `0.000e+00`, and the weighted mean of
`beta_gt + delta_gt * cellmean(x - xbar)` reproduces wooldid's `att_it` **exactly**, where `beta`
alone is off by `4.08e-03`.

**Verifier: confirmed**, with the finder's first remedy rejected, its scope corrected, and a sharper
defect identified. Refusing `gteffects` with `interactivecontrols()` by analogy with the
`contreat()` refusal at `4795-4796` would be an overreach: under `contreat()` dose zero is off the
support of the treated and the effect is a structural zero there, whereas the cohort's own covariate
mean is an interior, estimable, interpretable evaluation point, and the gap vanishes identically when
the weighted within-cell mean of the demeaned control is zero. The finder also missed that the help
*already* carries the cell-interpretation caveat it says is absent — sthlp:964-965 ("with
time-varying interactivecontrols() the interaction coefficients absorb control variation and the
cell-level reading is unreliable") and sthlp:953-954. Scope correction: "time-varying" is sufficient
but not necessary — on an *unbalanced* panel with a strictly time-constant interactive control the
identity also fails (`att` `1.9903978720` vs `1.9871236`), because the real condition is a non-zero
estimation-weighted within-cell mean of the cohort-demeaned control, which unbalance or weights
produce for any covariate. Both help sentences under-scope the caveat.

**The sharper defect.** sthlp:968-970 asserts the opposite of the reproduction: "Two reading notes:
the weighted-mean identity itself remains exact even under time-varying interactivecontrols() (the
caveat there concerns interpreting individual cells, not the aggregation)". That sentence is false,
and it contradicts sthlp:953-954 fifteen lines above it in the same paragraph. `git log -S` dates it
to `03094d1` ("add two verified reading notes to the help") — it shipped as a *verified* note,
presumably checked on a design where the gap is structurally zero (balanced and time-constant, or a
unit-level `i` where the slope columns drop). It matters because the help actively advertises the
re-aggregation workflow ("the table supports arbitrary custom aggregations") and PS-48 recommends
users re-aggregate `e(gteffects)` for a calendar-time estimand: a user doing exactly that silently
gets a number that differs from wooldid's own. wooldid's own reported aggregate is correct — margins
averages over the actual covariate values — so what is wrong is the cell estimand's label and the
documented identity. Corroborating: `5129` refuses the cell collapse on exactly this reasoning
("interactivecontrols() interacts the treatment dummy with a variable that varies inside a cell, so
the effect is no longer cell-constant") while the gteffects surface publishes a cell-constant number
for the same design with no run-time note.

**The two readings, for the author.** (a) *Document.* Mandatory either way: delete or invert
sthlp:968-970 and state the gap (the weighted mean of the cell slopes times the cells' own mean
demeaned covariate — a fraction of a percent in a typical design, unbounded in principle), widen the
qualifier at sthlp:953-954 and 964-965 from "time-varying" to the within-cell-mean condition, and add
a gated table note at `10001-10011` (gate on the returned `e(interactivecontrols)`, not the local, so
replay prints it too). (b) *Correct the cells.* Add one `gegen` per control for the
**estimation-weighted** within-cell mean of the demeaned copy (the tempvars are still in memory
between `1326` and `1950`), carry them into `gtraw`, and extend `wooldid_gtx` to parse the slope
columns and report `beta + sum_k delta_k * xbar_k,cell`. Two interface consequences: the SE stops
being a diagonal read (`var = var(beta) + xbar' V_dd xbar + 2 xbar' cov(beta, delta)`), so `gtsed`
must become the relevant submatrix of `e(V)` or the variance must be computed per cell; and bootstrap
propagation is free, since the per-rep harvest reads whatever `wooldid_gtx` produces. Test either
way: the fixture above asserting `sum(w*est)/sum(w) == e(b)` to 1e-10 for each of the four weight
columns — which fails today at `4.08e-03`/`6.84e-03` and passes under (b), or is inverted under (a)
to assert the documented gap equals `sum w delta xbar` — plus the unbalanced time-constant variant
and the two exactness controls.

  exactly (on the finder's 72-row panel, `att` reports `N = 56` and `att esfixedbaseperiod` reports

  the sample-formation sentence at sthlp:186-188 ("no untreated (including not yet treated) units
