## 1. The question as ruled by the author

## 2. What the code does

**Coefficient surface** - `wooldid_bootci` (def 12727), called from `wooldid_bootwire` (8721):

    if (ties) z0 = invnormal((sum(v :< cmp[kcol]) + 0.5*sum(v :== cmp[kcol]))/nn)
    else      z0 = invnormal(sum(v :<= cmp[kcol])/nn)        // 12795

`cmp` is the **rep-0 comparator**: `matrix `compname' = e(b)` (8254), taken right after a fastnose
run of the observed data inside `wooldid_bootrun` (8236-8253), and posted as the hidden
`e(boot_comparator)` (9211).

**Cell surfaces** - `wooldid_bootcellwire` (def 12115), called from `wooldid_bootcellsx` (6392-6393
for gteffects, 6418-6419 for each cfx matrix):

    b = M[i, obscol]                                          // 12142, the DISPLAYED cell estimate
    if (b >= .) continue                                      // 12143
    ...
    if (ties) z0 = invnormal((sum(v :< b) + 0.5*sum(v :== b))/n)
    else      z0 = invnormal(sum(v :<= b)/n)                  // 12168

So the two surfaces rank a different value against the same kind of draw set.

**Does a rep-0 cell comparator exist? No.** `wooldid_bootrun` mints the cell accumulators from the
rep-0 run's `e(gteffects)` (8318-8319) and `e(wdid_cfxmats)` (8326-8327) but keeps only the KEYS;
the rep-0 cell VALUES are discarded. The permutation engine does keep them - `wooldid_permrun`
mints the same keys (7262-7266) and then harvests the comparator cells with one extra call,
`mata: wooldid_bootcells("`cell0'", 1, `wdp_ncfx', ...)` (7270) - and `wooldid_permcellwire` ranks
the comparator cell (`sobs = C[1, k]`, 13471) while centring the interval on the displayed estimate
(`Mx[i, lbcol] = b - row[5]*so`, 13488). The bootstrap engine has no `cell0`.

**Where the two values could diverge.** The replications and the rep-0 run carry `fastnose`
(297, inside the `wdb_ro` build at 296-341); the observed run does not. So any quantity fastnose
changes makes the comparator differ from the displayed estimate. For the cell ESTIMATE columns:

- `gteffects` cells are raw stage-1 regression coefficients: `wooldid_gtx` sets `est = b[1, j]`
  (10808) from the `e(b)` of the still-live stage-1 model (block at 1910). fastnose changes margins
  and the VCE, never the fit, so column 5 cannot move.
- `cfx*` cells are `margins` point estimates: `matrix cfx... = f9tab[1..cfxmatendpoint, ...]'`
  (2720, 2757) with `f9tab = r(table)`. fastnose sets `cfxmatendpoint 1` (2664), truncating the
  matrix to the estimate column - but row 1 of `r(table)` is the same point estimate.
- The two ame screens that DO change reported numbers are both gated `fastnose == ""`: the R1
  scrub (1600) and the R6 void (1860). R1 scrubs columns `amescrublo = 2`..6, i.e. inference only.
  R6 (`amevoid`) sets `amescrublo = 1` (1876), which would blank the cfx ame ESTIMATE column - but
  those scrub loops are gated on `cfxmatendpoint > 1` (2759, 2848), false under fastnose. So under
  amevoid the observed cfx ame cell is missing while every replication cell carries the raw
  structural zero; `wooldid_bootcellwire` skips such cells anyway (12143).
- On the COEFFICIENT surface the same amevoid path does move a reported number: the voided ame
  entries re-enter `e(b)` as exact zeros (4249-4253) while the comparator keeps the fastnose run's
  raw value. That is the case the comparator convention was written for.

## 3. Method

There is no rep-0 cell comparator in `e()` to read, so the comparator run was **reproduced outside
the engine**: `wooldid` was run a second time on the same data under the replication option string
`wdb_ro` (296-341) - the point-estimate-shaping options plus `fastnose` - inside
`global WOOLDID_REPMODE 1`, which is what `wooldid_bootrun` itself does at 8243-8250.

The reproduction is **validated, not assumed**: the emulated run's `e(b)` is compared bitwise to the
engine's own hidden `e(boot_comparator)` from a real `bootstrap(standard)` run of the same
specification (section 4a). Where that check passes, the emulated run's `e(gteffects)` / `e(cfx*)`
IS the cell vector the engine would have harvested at rep 0.

Cells are matched between the two runs with the engine's own key function
(`wooldid_bootcellkey`), so a cell present in one table and not the other is counted, not silently
paired.

## 4. Results

### 4a. Calibration: the emulated comparator IS the engine's comparator

From `f018_d1.log` and `f018_d2.log`:

    F018|CALIB C1 cols=6,6   exactly_equal=1 maxabsdiff=0    (dta_binary, att)
    F018|CALIB D2 cols=12,12 exactly_equal=1 maxabsdiff=0    (dta_cont, contreat + lattice + makecfxplots)

The emulated rep-0 run's `e(b)` equals the engine's hidden `e(boot_comparator)` in every bit of
every column, on both the binary and the continuous-treatment specification - so the emulated cell
vectors are the ones the engine would harvest at rep 0. Two further sanity lines (`f018_d1.log`):

    F018|BOOTB C1 ndiff_vs_observed=0                 (e(b) after the bootstrap run is the observed b)

(The z0 and endpoint columns are exact for the gteffects rows - equal inputs, equal ranks. For the
two cfx rows they are the arithmetic bound of 4b's last paragraph plus the observation that no run

No cell was present in one table and missing from the other (`Aonly=0`, `Bmissing=0`), and no cell
estimate was missing on either side (`Amissing=0`) in any config.

Two different regimes, and the split is exactly the one the code predicts:

- **gteffects cells are bitwise identical** - 4,419 cells over five configurations (two datasets,
  the count leg and the physical re-id leg, weighted and unweighted, with and without subgroups),
  zero differences. These cells are stage-1 `e(b)` entries; fastnose cannot move them.
- **cfx cells differ in the last digits only** - all 6 differ, by 1.9e-11 relative on the ame
  matrix and 9.4e-14 on the att matrix. These come out of `margins`, and `margins ... nose` walks a
  slightly different numeric path than `margins` with a VCE. This is the "last digits ... for
  ame-family rows" the report anticipated, now quantified.

**Does that move z0?** No. z0 is a rank: `z0 = invnormal(#{v <= x}/n)`, so it changes only if a
draw falls between the two candidate values.

- For the **4,419 gteffects cells the two z0 values are identical, exactly and by construction** -
  the ranked values are the same double, so the counts, z0, both BC endpoints and the BC p are the
  same bits.
- For the **6 cfx cells** the ranked values differ, so the statement is probabilistic rather than
  exact: a z0 difference needs a draw inside a window about 2e-11 wide (ame; 1e-12 att) around the
  estimate. The measured bootstrap SDs of those very cells (from the same run) are 0.0094-0.0260
  for the ame matrix and 0.0152-0.0178 for the att matrix, so the gap is 2.0e-9 draw SDs (ame) and
  6.1e-11 (att). The expected number of draws inside the window at 199 replications is
  n*phi(z0)*d/se ~ 199 * 0.4 * 2.0e-9 = about 1.6e-7 per cell (ame; 5e-9 att). It stays negligible
  at any replication count a user would run: at 1e6 replications the expected number of affected
  cells is still about 8e-4. No disagreement was produced by any run here.

CAVEAT worth stating plainly: the cfx arm is 6 cells on one small dataset, because dta_cont's
lattice(all 3) yields three lattice points per matrix. The mechanism (margins-with-nose numerics),
not the cell count, is what carries the conclusion - but a wider cfx sweep is the one cheap thing
that would harden it.

## 5. How big would a comparator gap have to be to matter? (`f018_d4.do`)

The measured gaps are zero (gteffects) or 1e-11-ish relative (cfx), so "how often do they differ"
answers itself on these data. To say what the answer would become if a gap were ever material, the
rank arithmetic was simulated directly: 199 draws, level 95, gap `d` in units of the draws' own
standard deviation, 4,000 replications per row, using the engine's own order-statistic rule
(`wooldid_bootqs`).

| gap d (in draw SDs) | P(z0 differs) | mean abs dz0 when it does | P(a BC endpoint moves) | mean shift (draw SDs) | max shift |
|---|---|---|---|---|---|
| 1e-12 | 0.0000 | - | 0.0000 | - | - |
| 1e-9 | 0.0000 | - | 0.0000 | - | - |
| 1e-6 | 0.0000 | - | 0.0000 | - | - |
| 1e-4 | 0.0070 | 0.0131 | 0.0035 | 0.094 | 0.394 |
| 1e-3 | 0.0798 | 0.0133 | 0.0380 | 0.101 | 0.678 |
| 1e-2 | 0.5513 | 0.0185 | 0.3515 | 0.095 | 0.771 |
| 5e-2 | 0.9830 | 0.0514 | 0.9225 | 0.164 | 1.142 |

That block is z0 target 0 with no ties. Three further blocks were run - z0 target 0.5, and tie
masses of 10% and 30% of the draws sitting exactly on the observed value. All agree: P(z0 differs)
is 0.0000 at d = 1e-12 and 1e-9 in every block, and the single non-zero entry below d = 1e-4
anywhere in the four blocks is 0.0003 at d = 1e-6 under the 10% tie mass - the tie-flip channel
behaving as expected. At d = 1e-3 the four blocks give 0.080, 0.074, 0.069 and 0.077.

The gaps actually observed are 0 (gteffects cells), 2e-9 draw SDs (cfx ame cells), 6e-11 (cfx att
cells) and 3e-15 (dta_binary coefficients) - between five and twelve orders of magnitude below the
smallest gap that moved anything in the simulation. Note also what the right-hand columns say about
the stakes even when a flip does happen: one flipped rank is dz0 ~ 0.013 and a BC endpoint move of
about a tenth of a bootstrap SD.

## 6. Two things found on the way (not part of the ruling; for your judgment)

**(a) The cell accumulator keys are minted from the REP-0 run's `e()`, not the observed run's.**
`wooldid_bootrun` runs the rep-0 comparator at 8236-8253 and does not restore the observed
estimates before minting the keys - there is no `estimates restore` between the comparator
assignment (8254) and the key minting (8318), 64 lines that can be checked by eye. So the reads at 8287 (`e(wdid_sglist)`), 8318-8319 (`e(gteffects)`) and 8326-8327
(`e(wdid_cfxmats)`) see the fastnose rep-0 run's e(), while the comment directly above them at 8313
says "Built while the OBSERVED e() is live, so the keys are the observed cells". The measurements
here show the two key sets do coincide on every configuration tested (`Aonly=0` in every row of the
4b table, so no observed cell lacked a rep-0 key, and the cfx matrix NAME lists match:
`CFXMATS obs = cfxame_cfxpost cfxatt_cfxpost` equals `CFXMATS cmp`). Nothing is lost today. The
failure mode if they ever diverged is silent: `wooldid_bootcellwire` leaves a keyless cell's
se/p/lb/ub missing (12140), and an observed-only `cfx*` matrix would get no accumulator at all and
would keep its analytic inference inside a bootstrap run. Cheapest repair is to correct the
comment; the safer one is to key from the stored observed results.

**(b) The one structural place the two conventions really part company.** Under `amevoid`
(SI-A4/R6, 1860-1878) the observed run blanks the cfx ame ESTIMATE column (`amescrublo = 1`), while
the replications - which never fire the screen; it is gated `fastnose == ""` - carry the raw
structural zeros. The displayed cell is then missing and `wooldid_bootcellwire` skips it (12143),
so no interval is built under either convention. Moving z0 to a comparator would not resurrect
those cells, and should not: the estimate itself is withheld by design. The divergence exists, and
it is already handled by the missing-estimate guard rather than by the z0 rule.

## 7. Conclusion

1. **The bootstrap engine has no rep-0 cell comparator to move z0 to.** It mints the cell
   accumulator keys from the rep-0 run and discards that run's cell values; only the permutation
   engine keeps them (`cell0`, 7270, consumed by `wooldid_permcellwire` as `sobs = C[1, k]`, 13471).
   "Move the cell z0 to the comparator convention" is therefore not a one-word change - it needs
   the rep-0 cell vector plumbed through.

2. **No cell examined has a different z0 under the two conventions - 0 of 4,425.** The claim is
   exact for 4,419 of them and probabilistic for 6. For the 4,419 gteffects (five configurations, two datasets, both bootstrap legs, weighted and unweighted, with and
   without subgroups) the ranked values are bitwise identical, so z0, the endpoints and the BC p
   are the same bits - exact, and structural: gteffects cells are stage-1 `e(b)` entries and
   fastnose does not touch the fit. For the 6 cfx cells the ranked values differ in the last digits
   (1.9e-11 relative on the ame matrix, 9.4e-14 on the att matrix - `margins ... nose` numerics),
   which is 2e-9 bootstrap SDs; the chance a draw sits in that window and flips the rank is about
   1.6e-7 per cell at 199 replications, and no run here produced one. That last part is an
   arithmetic bound plus observation, not a bitwise proof - the cell draws are not retained in e(),
   so a direct per-cell z0 recomputation is not available for cfx without a code change.

3. **Even where the two values genuinely differ - the coefficient surface - the convention changed
   nothing.** Across 30 coefficient columns in three specifications, 16 of them with a non-zero
   comparator gap (including all 12 columns of the contreat + lattice + makecfxplots run, where the
   gap reaches 3.5e-10), z0, both BC endpoints and the BC p were identical under both conventions
   in every single column. The recomputation
   used here reproduces the engine's own `e(boot_z0)` exactly, so this is the engine's arithmetic,
   not a re-implementation of it.

4. So F018 is a **consistency wart, not a defect that has ever moved a reported number**. The two
   surfaces answer the same question with two different inputs that are, in practice, the same
   number.

## 8. Recommendation (for your ruling - nothing was changed)

**Primary: close F018 as immaterial, and spend the effort on documenting the convention rather
than changing it.** A fix buys no number on any surface measured. What is missing is the reason,
which today has to be reassembled from four places in the file. Concretely:

- a comment at `wooldid_bootcellwire` (at the `sum(v :<= b)` line, 12168) recording that the cell
  surface ranks the DISPLAYED estimate deliberately; that for gteffects this is the rep-0
  comparator value bitwise (those cells are stage-1 `e(b)` entries, which fastnose cannot move) and
  for cfx cells it differs only in `margins`-with-nose last digits (~2e-9 bootstrap SDs measured);
  that the amevoid case is caught by the `b >= .` guard; measured 2026-09-06, 0 of 4,425 cells;
- the same sentence in the report's F018 row, moved from "not fixed" to "ruled: immaterial, with
  evidence";
- fix the stale comment at 8313 (item 6a), a one-line change that stops a future reader concluding
  the accumulator keys are the observed run's.

There is also a positive reason to prefer the current cell rule, not merely tolerate it: Efron's z0
ranks theta-hat, the statistic whose sampling distribution the draws estimate - which on the cell
surface is the displayed estimate, the number the table reports and the interval is built around.
The comparator convention on the coefficient surface exists to neutralise a fastnose-vs-full-model
offset (amendment A3) that the cell surface has essentially none of.

**Secondary, only if you want engine symmetry for its own sake.** F067 has just landed, and with it
a second consumer of the same z0: `bootdisplay(bca)` takes "z0 as the BC family's" for coefficients
(8723) while the cells fall back to the bc family entirely (6354-6359, with a caution). So the
F018 asymmetry now also decides what the cells show under `bootdisplay(bca)`. If that argues for
symmetry, the change is: in `wooldid_bootrun`, right after the key minting at 8318-8327 - where
`e()` is still the rep-0 run's, which is exactly why it works there - add the
`mata: wooldid_bootcells("`cell0'", 1, `wdb_ncfx', ...)` call that `wooldid_permrun` already makes
at 7270; thread a `cell0()` option through `wooldid_bootcellsx` into a new comparator argument of
`wooldid_bootcellwire`; and rank `cmp[k]` there instead of `b`, keeping the interval centred on `b`
exactly as `wooldid_permcellwire` does (13471 vs 13488). About 15 lines in four places, plus a
hidden `e(boot_cellcomparator_*)` post if you want it reproducible from e() the way permute's
`permcmp_*` is. Two provisos: keep a fallback to `b` when the comparator cell is missing, or cells
absent from the rep-0 harvest silently lose the BC family they have today; and make `bca` read the
same z0 source rather than minting a third.

**Do not** build a middle option (compute both, caution on disagreement): the measured disagreement
rate is zero, and the pathological-data effort cap applies.
