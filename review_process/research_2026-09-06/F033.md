# F033 - two p-value conventions on one bootstrap surface

**Status: research record, no code change made.** Author ruling on F033 was MORE RESEARCH:
"measure the SIZE of the bootstrap joint tests under both conventions at reps 99, 199 and 999."

## 1. The question as ruled

One bootstrap table prints two rank-p conventions:

| surface | construction | convention | code |
|---|---|---|---|
| coefficient / contrast p, no `boottstat` | `2*min(m0,m1)/n` where `m0 = #{b_r <= 0}`, `m1 = #{b_r >= 0}` on the **raw** draws - the exact inversion of the percentile interval | **no add-one** | `wooldid_bootci` (fn at 12595; the p at 12661) |
| coefficient / contrast p, under `boottstat` | `2*min(m0,m1)/n` where `m0 = #{t_r <= t_obs}`, `m1 = #{t_r >= t_obs}` on the **recentred** draws `t_r = (b_r - b_obs)/se_r` | **no add-one** | `wooldid_boottp` (fn at 11375; the p at 11435) |
| joint pre-trend / adversarial / subgroup-equality p | `(1 + #{W_r >= W_obs})/(n + 1)` on recentred `W_r` | **add-one** | `wooldid_bootqf` (fn at 13081; the p at 13124) - fixedmetric; `wooldid_bootjnt` 6594 / 6615, adversarial 6666 - studentized |

The ruled question: does the convention change the **size** of the joint tests, and by how much,
at `reps(99)`, `reps(199)`, `reps(999)`?

*Line numbers are as of 2026-09-06 after `dc3f345` (F064). The file moved during this item's
runs - the F064 commit landed mid-session - so cite the function names, not the lines. F064
touched the permutation p-value conventions and added the bootstrap tail record; it did not
touch `wooldid_bootqf` or the joint-test block, and every run below reproduced
`e(joint_horiz)` from `(1 + X)/(n + 1)` bit for bit, so the arms are on the shipped statistic.*

## 2. Method

Two parts, because the question turns out to have an exact answer plus an empirical residual.

**(a) Exact enumeration.** Both p-values are functions of one integer: `X = #{W_r >= W_obs}` for the
one-sided joint test, `m = min(m0, m1)` for the two-sided coefficient p. A rejection at nominal
`alpha` is therefore a statement about an integer lattice, and the two conventions' rejection sets
can be compared exactly, with no simulation. Under the reference assumption that the observed
statistic is exchangeable with the `n` replication statistics (the Monte-Carlo-test premise: the
rank of the observed statistic among the `n+1` values is uniform), the size of each rule is an
exact rational number. Script: `lattice.py` / `lattice2.py` (below).

**(b) Simulation.** A null staggered panel: 24 units (= 24 clusters) x 8 periods, cohorts `ttre = 4`
(units 1-8) and `ttre = 6` (units 9-16), 8 never-treated; `y = a_i + 0.05*t + e_it` with
`a_i ~ N(0,1)` and `e_it` an AR(1), `rho = 0.5`, innovation `N(0,1)`; **no treatment effect**.
Call: `wooldid y unit t ttre, att cluster(unit) esprelength(3) espostlength(1) jointtests
bootstrap(standard) reps(R) rseed(.)`. Recorded per dataset: `e(joint_horiz)` (the shipped add-one
p), and `n`, `X`, `W_obs` recovered from `e(boot_jointW)` / `e(boot_jointWobs)`, from which the
no-add-one p `X/n` is computed on the same run.

## 3. Result (a): the exact enumeration - this settles the ruled question

Reject when `p <= alpha` (the usual reading). Write `X = #{W_r >= W_obs}` and `n` = listwise-complete
replications actually used.

* add-one rejects iff `X <= alpha*(n+1) - 1`; no-add-one rejects iff `X <= floor(alpha*n)`.
* `alpha*(n+1) - 1 = alpha*n - (1 - alpha) < alpha*n`, so **the add-one rejection set is always a
  subset of the no-add-one one: add-one is weakly conservative, never anti-conservative.**
* They differ by exactly one lattice point iff `frac(alpha*n) < 1 - alpha`; i.e. they **coincide**
  iff `alpha*(n+1)` is an integer. (That last equivalence uses `1/alpha` integer, which holds for
  the .05 and .10 tabulated here; at other levels - `level(97)`, say - the coincidence set is
  wider and must be read off `frac(alpha*n) < 1 - alpha` directly.)
* When they differ, the size gap is exactly `1/(n+1)` under exchangeability.

**At exactly the three replication counts the author named - 99, 199, 999 - and at both nominal
levels, the two conventions have identical rejection sets and identical exact size (= alpha).**
That is why those R are the textbook choices: `alpha*(R+1)` is an integer for alpha = .05 and .10
simultaneously. A simulation at those R cannot separate the conventions; it can only measure how
often the two agree, which is always.

The conventions separate at every other R. The cost of no-add-one is worst where users are most
tempted to economise: at `reps(20)` the no-add-one joint p would reject 9.5% of the time at a
nominal 5% (exactly twice the nominal level), at `reps(49)` 6.0%, at `reps(100)` 5.9%. The add-one
form is exact-or-conservative at every n (`size_add = floor(alpha*(n+1))/(n+1) <= alpha`), which is
the classical Dwass/Barnard Monte-Carlo-test property and the reason Davison and Hinkley (1997,
s4.2.3, eq. 4.11) recommend it for bootstrap tests generally.

### The `p <= alpha` vs `p < alpha` reading matters as much as the add-one choice

| n | alpha | one-sided add | one-sided no | two-sided add | two-sided no |
|---:|---:|---:|---:|---:|---:|
| 99 | .05 | .04000 | .05000 | .04000 | .06000 |
| 199 | .05 | .04500 | .05000 | .04000 | .05000 |
| 999 | .05 | .04900 | .05000 | .04800 | .05000 |
| 99 | .10 | .09000 | .10000 | .08000 | .10000 |
| 999 | .10 | .09900 | .10000 | .09800 | .10000 |

(strict `p < alpha`). Under strict inequality the conventions no longer coincide at 99/199/999: the
add-one p attains alpha exactly (p = 5/100 at n = 99) and a strict reader throws that point away.
A user who filters `if p < .05` gets a 4% test from the add-one convention and a 5% test from the
other. This is a reporting hazard the help does not mention and is larger, at these R, than the
convention difference itself.

## 4. Result (b): the simulation

### 4.1 Arm A - balanced null panel, `reps(99)`, S = 8 datasets

Every replication was listwise complete, so `n = R = 99` in all 8 runs and the lattice
alignment held. The recomputed add-one p reproduced `e(joint_horiz)` to the last bit in every
run (max |difference| = 0), which validates the extraction of `n` and `X` from
`e(boot_jointW)` / `e(boot_jointWobs)`.

* rejection rate at 5%: **0/8 under BOTH conventions**; at 10%: **0/8 under both**. Zero
  discordant decisions, as section 3 requires.
* `X/n` (the rank of `W_obs` among the recentred draws): mean **.556** against .500 under
  exchangeability; KS distance from U(0,1) = **.178** against a 5% critical value of .480.
  No evidence of miscalibration, and no power to find any: **S = 8 cannot estimate a 5%
  rejection rate** (0/8 is what a correctly sized test produces 66% of the time).

**The S the author's design called for (200 at R = 99/199, 100 at R = 999) was not
attainable.** On a quiet machine one `reps(99)` run of this fixture takes 17.3 s (timer 1 of
`timing.do`); during this session the box carried 8-10 competing Stata processes at load
19-34 and the same run took 3.7-4.8 minutes, i.e. about 2.2 s per replication instead of
0.17 s. The full three-arm design costs roughly 40,000 replications, which is ~2 hours solo
and ~24 hours at the throughput available. Arms at `reps(199)` and `reps(999)` were therefore
NOT run. Section 3 shows why that costs nothing for the ruled question - the conventions are
provably identical at 99, 199 and 999 - and the size-level measurement it does cost is
already scheduled: the F058 work item lists "fixed-metric tests" among the extended
calibration simulations, which is where it belongs, on a quiet machine.

### 4.1b The `boottstat` arm was NOT run

The author made it conditional on time, and there was none: a `boottstat` replication runs
without `fastnose` and, with `cluster()`, pays the physical re-identification leg on top, so
even `reps(99)` on this fixture would have cost several times an Arm-A dataset at the
throughput available. Nothing is lost for the ruled question. The studentized joint p is the
**same one-sided add-one form** as the fixed-metric one - `(1 + #{W_r >= W_obs})/(n + 1)`,
`wooldid_bootjnt` 6594 (overall) and 6615 (per subgroup) - so section 3's enumeration applies
to it verbatim, including that 99, 199 and 999 are aligned at both levels. Its `n` is the count
of usable `W_r` in `e(boot_jointW)`, which is again <= `reps()` (a replication whose own
`e(V_es_*)` was rank-deficient contributes no `W_r`) and again invisible in the output.

One thing is worse there: **`e(boot_jointWobs)` is posted only on the fixed-metric branch**
(`wooldid.ado` 6561; the studentized branch at 6620 posts `e(boot_jointW)` alone, and the help
says so at L1062 - "the latter two without boottstat"). So under `boottstat` the no-add-one p
cannot be recomputed from `e()` at all; it can only be backed out by inverting the shipped p
for `X` after hand-counting the non-missing rows of `e(boot_jointW)`. That makes recommendation
3 below - post the joint test's own `n` - more, not less, worth doing.

### 4.2 Arm B - the case the identity does not survive: `n < R`

The section-3 identity holds only when `n`, the number of **listwise-complete** replications
over the tested pre-horizons, equals `R`. It is not the user's `reps()`: `wooldid_bootqf`
drops any replication missing any tested column. Arm B builds a null panel where one horizon
is identified by a small cohort - 24 clusters, units 1-2 treated at `t = 4` (the only source
of relative year -3), units 3-14 treated at `t = 3` (relative years -1, -2 only), 10 never
treated - so a resample that misses both of units 1-2 (probability `(22/24)^24 = .124`) loses
the pre3 column and is dropped from the joint test.

|---:|---:|---:|---:|---:|:--:|:--:|---:|
| 1 | 88 | 79 | .8989 | .8977 | 3/4 | -,- | .0449 / .0562 |
| 2 | 88 | 0 | .0112 | **.0000** | 3/4 | R,R | .0449 / .0562 |
| 3 | 84 | 46 | .5529 | .5476 | 3/4 | -,- | .0471 / .0588 |
| 4 | 89 | 0 | .0111 | **.0000** | 3/4 | R,R | .0444 / .0556 |
| 5 | 86 | 3 | **.0460** | **.0349** | 3/4 | R,R | .0460 / .0575 |
| 6 | 87 | 36 | .4205 | .4138 | 3/4 | -,- | .0455 / .0568 |
| 7 | 84 | 28 | .3412 | .3333 | 3/4 | -,- | .0471 / .0588 |
| 8 | 87 | 0 | .0114 | **.0000** | 3/4 | R,R | .0455 / .0568 |

Four findings, all from 8 runs:

1. **`n` was never 99.** It took the values 84, 84, 86, 87, 87, 88, 88, 89 - always short, and
   random. The dropped counts (`R - n` = 11, 11, 15, 10, 13, 12, 15, 12) average 12.4 of 99 =
   **.125**, against the predicted `(22/24)^24 = .124`; the mechanism is exactly the one
   designed in. The user cannot choose an aligned `n` by choosing `reps()`; alignment is decided by
   the resampling. At every one of those `n` except 89 at the 10% level, the two conventions
   have **different** rejection sets (thresholds 3 vs 4 at 5%), with exact sizes .0444-.0471
   for add-one against .0556-.0588 for no-add-one - the add-one form conservative, the other
   anti-conservative by about `1/(n+1)`, i.e. slightly more than one percentage point.
2. **The no-add-one p prints exactly 0 in 3 of 8 runs** (`X = 0`), where the add-one p prints
   .0111-.0114. This is finding F038 in one line: dropping the add-one would put a literal
   zero into the joint-test row of a table whose evidence supports only "below 1/89".
3. **The p-values differ visibly even where the decision agrees.** Dataset 5: .0460 against
   .0349 on the same run - a 32% relative difference, and either side of .04 on a reader's eye.
   In the rejection region the gap is exactly `(n - X)/(n(n+1))`, which is `~1/(n+1)`: one
   percentage point at `reps(99)`, one tenth of one at `reps(999)`.
4. **A side finding, not about conventions.** 4 of 8 null datasets rejected at nominal 5%
   under both conventions. Exact binomial: P(>= 4 of 8 | size .05) = .00037, so the
   fixed-metric joint test is genuinely oversized in this configuration. The *likely* cause -
   not established from 8 runs - is structural rather than a convention: the pre3 horizon rests
   on 2 clusters, its bootstrap covariance is nearly singular, and `W_obs` explodes (dataset 2:
   `W_obs` = 20.7; dataset 8: `W_obs` = 36.2). A competing explanation not ruled out here is
   conditional selection: the replications that survive are exactly those that drew units 1-2,
   so the retained draw distribution is conditioned on an event the observed estimate is not
   conditioned on, which shifts the draws relative to `b_obs` (the F018 recentring family). This is the MacKinnon-Webb few-treated-clusters regime the help already
   warns about for the pairs cluster bootstrap, now visible in the joint test. **Neither
   convention protects against it** - the add-one form is a one-lattice-point correction, not
   a calibration. Worth a line in the F058 calibration work.

### 4.3 The joint test's `n` is invisible in the output

`probe.do`, one Arm-B dataset at `reps(99)`:

```
PROBE joint-test n = 88   X = 0   p_add = 0.01123596   p_no = 0.00000000
PROBE e(boot_completed) = 99
PROBE e(boot_failed)    = 0
PROBE e(boot_N_V)       = 88
PROBE e(joint_horiz)    = .01123596
footer line             : "The rank-based p-values have resolution 2/99 = 0.020"
```

Nothing printed tells the reader that the joint test used 88 replications, and the one line
that speaks to resolution states the wrong one for it three times over: the joint p is
one-sided (1/(n+1), not 2/n), it is add-one, and its `n` is 88, not `e(boot_completed)` = 99.
Its true resolution here is 1/89 = .0112. `e(boot_failed)` is 0, so nothing in `e()` flags the
shortfall either; the only way to recover `n` is to count the non-missing rows of
`e(boot_jointW)`. (`e(boot_N_V)` = 88 shows the coefficient covariance is listwise too, and
`wooldid_bootci` takes its `nn` per column, so within one table different rows can sit on
different lattices.)


## 5. Reading of the code's own justifications

The review's CLAIM is that `wooldid_bootjwr`'s comment ("unlike the percentile p on raw coefficient
draws, this IS a reference distribution simulated under the null") does not hold, because `W_r` is
recentred at `b_obs` exactly as `t_r` is. That is right **against `wooldid_boottp`** and wrong
against `wooldid_bootci`:

* `wooldid_bootci` (no `boottstat`) does not rank an observed statistic at all. It locates the null
  value 0 among the raw draws, and the p is the exact inversion of the percentile interval printed
  beside it. No observed statistic joins a reference set, so there is nothing for add-one to add,
  and adding one would break the interval duality the code measured on purpose (its own count:
  6 boundary disagreements under the shipped rule against 36 under two-sided add-one, over 35,646
  constructed cases, `wooldid_bootci` 12637-12655, the count at 12646). The comment's justification holds here.
* `wooldid_boottp` (under `boottstat`) **does** rank an observed statistic - `t_obs` - among `n`
  recentred null draws `t_r`. That is structurally the same object as the joint test's
  `#{W_r >= W_obs}`, differing only in being two-sided. The comment's justification does not hold
  here, and this is the real inconsistency: two rank-of-the-observed-statistic tests on one table,
  one add-one and one not. Its cost is quantified in the second table of section 3 - at `reps(99)`
  and 5% the studentized coefficient p is a 6% test where the joint p on the same table is a 5% one.

So the surface carries not two conventions but three constructions, of which two are the same
construction under different conventions.

## 6. Conclusion

1. **The ruled question has an exact answer and the simulation was not needed to get it.** For
   the one-sided joint / adversarial / subgroup-equality rank test, at `reps(99)`, `reps(199)`
   and `reps(999)` and at both the 5% and 10% levels, the add-one and no-add-one conventions
   have **identical rejection sets and identical exact size (= alpha)**. `alpha*(R+1)` is an
   integer at all three R for both levels; that is precisely why those R are the textbook
   choices. Arm A confirms it on real runs: 8 of 8 datasets, zero discordant decisions.
2. **Where they differ, add-one is the conservative one and it is never anti-conservative.**
   The add-one rejection set is a subset of the other at every `n`; the exact sizes are
   `floor(alpha*(n+1))/(n+1) <= alpha` for add-one and `(floor(alpha*n)+1)/(n+1)`, which
   **exceeds** alpha whenever the two differ, for no-add-one. The gap is exactly `1/(n+1)`.
   It is severe at small `n` - `reps(20)` would make the no-add-one joint p a 9.5% test at a
   nominal 5% - and shrinks to .001 by `n = 1000`. So the difference does "vanish by R = 999"
   in magnitude, but it is already exactly zero at R = 99 and R = 199 for the shipped shape.
3. **The identity is a knife edge the user does not control.** The joint test runs on
   listwise-complete replications, and Arm B - one pre-horizon identified by a 2-cluster
   cohort - produced `n` in {84, 86, 87, 88, 89} in 8 of 8 runs at `reps(99)`, never the
   aligned 99. At those `n` the conventions genuinely differ, add-one at .044-.047 and
   no-add-one at .056-.059 against nominal .05. This is the case that decides the ruling:
   under add-one the test stays valid whatever `n` turns out to be; under no-add-one its
   validity depends on a number the user cannot see and did not choose.
4. **The inconsistency the review reported is real, but it is between the joint p and
   `wooldid_boottp`, not between the joint p and `wooldid_bootci`.** `wooldid_bootci` does not
   rank an observed statistic - it inverts the percentile interval by locating 0 among raw
   draws - so there is nothing for add-one to add, and its comment's justification holds.
   `wooldid_boottp` does rank an observed statistic (`t_obs`) among recentred null draws,
   exactly as the joint test ranks `W_obs` among recentred `W_r`, and uses the other
   convention. At `reps(99)` and 5% that costs it: the two-sided no-add-one rule has exact
   size **.06** there, against .04 for its add-one counterpart. `reps(99)` is aligned for the
   one-sided joint test and NOT aligned for the two-sided coefficient p; `reps(199)` and
   `reps(999)` are aligned for both.
5. **The `p <= alpha` vs `p < alpha` reading is the larger hazard at these R.** Under strict
   `<`, the add-one joint p at `reps(99)` is a 4% test and the no-add-one one a 5% test - a
   bigger wedge than the convention itself opens at any of the three R. Nothing in the help
   warns that the add-one p attains alpha exactly (5/100 at `reps(99)`).
6. **The size level of the fixed-metric test is not measured here** and could not be within
   this session's compute. Arm A gives no evidence of miscalibration on a balanced 24-cluster
   panel (rank uniform, KS .178 vs .480) at S = 8; Arm B shows a clear oversizing (4/8, exact
   binomial p = .00037) when a horizon rests on 2 clusters, which is a few-clusters problem and
   not a convention problem.


## 7. Recommendation for the author to rule on

**Primary (keep the add-one on the joint family; do not unify the engine).** The two
constructions are different objects and each convention is right for its own: `wooldid_bootci`
inverts an interval (add-one would break the duality the code measured on purpose - 6 boundary
disagreements against 36), while the joint / adversarial / subgroup-equality p ranks an
observed statistic among simulated null draws (add-one is what makes it exact-or-conservative
at every `n`, which matters because `n` is not `reps()` and the user cannot see it). Do not
adopt one convention across the engine. Instead:

1. **Fix the real inconsistency: `wooldid_boottp`.** It is the same construction as the joint
   test under the other convention, and at `reps(99)` / 5% that makes it a 6% test where the
   joint row on the same table is a 5% one. Two defensible resolutions, the author to pick:
   (a) move it to two-sided add-one `2*(1 + min(m0,m1))/(n+1)`, which costs its duality with
   the percentile-t interval printed beside it (the same cost `wooldid_bootci` declined to
   pay), or (b) leave it and say in the help that it is the interval-dual rank p and is
   anti-conservative by one lattice point whenever `alpha*(n+1)/2` is not an integer. **(b) is
   the cheaper and, given the duality argument the code already won, the more consistent
   choice.** Either way the help should stop presenting the two conventions as unexplained
   (L487, L492).
2. **Document the lattice, once, with the numbers.** Add to `reps()`: choose `reps()` so that
   `alpha*(reps+1)` is a whole number - 99, 199, 999 for the one-sided joint tests at both 5%
   and 10%; 199 and 999 for the two-sided coefficient p at 5% (99 is not aligned for it, and
   the help's own worked example `reps(500)` is aligned for neither). State that the add-one p
   attains alpha exactly there, so a strict `p < alpha` filter turns a 5% test into a 4% one.
3. **Post and print the joint test's own `n`.** `e(boot_completed)` = 99 while the joint test
