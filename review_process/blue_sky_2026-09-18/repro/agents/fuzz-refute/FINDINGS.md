# fuzz-refute — skeptic verdicts on FUZZ-01..08, plus what I found while refuting

Build asserted in every log: `which wooldid` -> `.../bluesky/build/wooldid.ado`, `*! version 1.4`.
All data generated by me. The project test suite was never touched.
Every repro below is self-contained and was RUN from a clean Stata: see `repro/*.log`.

## VERDICTS

### FUZZ-01 contreatelasticitytype() relabels a binary ATT table — **CONFIRMED** (severity revised high -> medium)
repro: `repro/REPRO_F01_elasticity_header.do`  (log `repro/REPRO_F01_elasticity_header.log`)

Reproduced on my own 60-unit panel. `contreatelasticitytype(dydx|dyex|eydx|eyex)` with no
`contreat()`: rc 0 for all four; `att` and `se` **bit-identical** to the baseline
(`bitidentical_b=1 bitidentical_se=1`, baseline `+1.ee91e03e4b112X+000` / `+1.ea4cb758a6a5eX-005`);
the header becomes `Main Results (Full Estimation Sample): Marginal Treatment Effects Presented
as Elasticities` (and the (eydx)/(dyex) variants) over a level ATT whose design truth is 2.
The bare-`wooldid` replay reprints the same header, so the mislabel is stored, not transient.

**The decisive evidence the prober missed** is in the help he did not quote. `sthlp:908`:

> "A supplied value outside this list is rejected with an error, whether or not contreat(varname)
> is specified; **without contreat(varname) the option is otherwise inert, its value read by
> nothing and no message printed.**"

The code reads it at `ado:11283` (`local contreatelasticitytype \`e(wdid_cetype)'`) and prints at
`ado:11314-11317`, with no `contreat()` gate. So this is not an open design question ("should it
refuse?") — the author has already published the intended behaviour and the code does not do it.
The internal comment at `ado:5028-5030` says the same thing ("without contreat() has no
requires-parent screen and is inert").

Two corrections to the claim:
1. "posts nothing to e(contreatelasticitytype)" — it **does** post `e(wdid_cetype)` (hidden), and
   that is exactly what the replay header reads. What is missing is a *visible* return.
2. "Every other contreat() companion is refused r(198) in that same position" — **false**.
   Refused (4): `lattice()`, `contreatcontrols()`, `contreatwithin`, `makecfxplots`.
   Accepted rc 0 (7 more): `latticeignoreweights`, `ccnoabsorb`, `contreatpoly(2)`,
   `cfxplottypes()`, `makecfxplotsbysg`, `cfxplotnose`; plus `cfxlattice()` which is accepted
   **with** an explicit "has no effect ... and is being ignored" Caution. So inertness is the
   norm, and the parity argument is weaker than stated. What is unique to
   `contreatelasticitytype()` is being inert *and* rewriting the header.

Severity: the number is right; only the label is wrong. That is brief-ladder #5/#6, not #1.
Revised to **medium**.

### FUZZ-02 semi-elasticity dies with a raw Mata error — **CONFIRMED**, mechanism partly corrected (severity medium kept)
repro: `repro/REPRO_F02_semielasticity.do`

Built a realistic zero-straddling outcome (an annual growth rate, range -1.858 .. 2.161) and
reproduced independently. Corrections:

1. **Which raw error fires is context-dependent, not data-dependent.** The prober put r(3598)
   only on `i=unit + safety(off)`. On my single growth-rate panel **all four direct** wooldid
   configurations give r(3598), while the `permute()` path on **the same data** gives r(459) - so
   his 459-dominant results are not wrong, and the split is not about the data. The traceback is
   `variable __00001O not found / st_data(): 3598 / __marg_cr_eval() / deriv__call2user_v() /
   _deriv() / st__marg_cr_compute()`, on `cluster(i)` with safety ON, on `i=cohort`, and under
   `nofastcollapse`. The control without `semielasticity` is rc 0. (A wooldid tempvar being gone
   by the time margins' numerical-derivative pass re-evaluates the prediction is the obvious
   reading of that traceback, but I did not verify it and it is a hypothesis, not a measurement.)
2. **r(459) is genuine margins pass-through, and only r(3598) is wooldid's.** On a hand-fitted
   equivalent model (`reghdfe g x1 i.icoh#i.t#i.D, absorb(i t) vce(cluster i)`), plain
   `margins, dydx(x1)` is rc 0 and plain `margins, eydx(x1)` is **r(459)** with the identical
   "could not calculate numerical derivatives" text. So the 459 leg is not a wooldid defect;
   the tempvar-not-found leg is.
3. **The "nofastcollapse is the remedy wooldid's own Caution names" reading is a misreading.**
   That Caution is about the cell collapse; it ends "Specify nofastcollapse to silence this and
   evaluate every run on the full data" and states "the run is slower, and **no answer changes**".
   It never offers nofastcollapse as a fix for anything. That nofastcollapse does not help is
   therefore not a doc-vs-actual divergence.
4. **The trigger is sharper than "the outcome straddles zero".** Shifting the outcome by +1
   leaves the raw minimum at -0.858 (still straddling) but lifts the minimum saturated cell mean
   from -0.249 to +0.751, and the run returns rc 0. The predicate is the minimum cell-level
   fitted value, not the outcome range.
5. The `permute()` leg reproduces verbatim: `Error: the observed comparison statistic for att
   could not be read from the rep-0 run; permutation inference is impossible.` (rc 459).

### FUZZ-03 level(99.9)/level(99.99) refused — **CONFIRMED in substance, mechanism PARTIAL** (severity medium, unchanged)
repro: `repro/REPRO_F03_level.do`

Refused through wooldid with Stata's "level() can have at most two digits after the decimal
point": 99.9, 99.99, **95.4, 99.1, 90.1** (the last three are mine; the prober found only the
first two). Accepted: 95, 99.5, 97.5, 99.95, 99.8, 99.7, 99.75, 84.13, 68.27, 92.5, 90.25.
Plain `set level` accepts every one of them.

**"The levels it accepts are exactly the binary-representable ones" is false.** 99.95, 68.27,
84.13, 92.5 are not exactly representable and are all accepted. The real mechanism, measured:
Stata renders the result of a macro `=` at **16 significant digits**, and `set level` parses the
**literal text**. `syntax , Level(real 0)` echoes 99.9 as `99.90000000000001`, 99.99 as
`99.98999999999999`, 95.4 as `95.40000000000001`, while 99.95 and 68.27 round-trip short. And
`set level 99.9000` / `set level 99.900` are themselves refused r(198), which proves the check is
textual.

Mapped exhaustively (`pD_level_state.log`, agreeing exactly with an independent Python
reproduction of `%.16g`): **1152 of the 9000 two-decimal levels in [10, 99.99] break**, the first
at 64.01; and **144 of 900 one-decimal levels**, of which 40 lie in [90, 100): 90.1, 91.1, ...,
99.1, 99.4, 99.6, 99.9. Nothing below 64 breaks.

Severity stays **medium** for the claim as filed. The wider surface — the same re-render applied
to `c(level)`, which needs no `level()` option at all — is carried separately as NEW-1 below, so
it is not double-counted here.

### FUZZ-04 estimates replay fails — **CONFIRMED**, one sub-claim **REFUTED**, severity RAISED low -> medium
repro: `repro/REPRO_F04_replay.do`

`estimates store m1` rc 0; `estimates replay m1` r(198) "Error: command line input should feature
all of y i t ttre; too few variables specified." Confirmed.

**REFUTED sub-claim: "even a trailing blank defeats it."** From a clean state, `wooldid` followed
by two trailing blanks returns **rc 0** and replays the table. The prober's r(198) for that case
was the poisoned-global refusal below, misattributed. The gate at `ado:26` is
`if \`"\`0'"' == ""`, and Stata has already stripped the trailing blanks by then.

**Bigger than reported, and it contradicts the stated premise of a ruled entry.**
`known_bydesign.md §6` records `WOOLDID_LASTRC` as author-directed replay design (NFRPL-01/02),
and `ado:27-30` does say the marker fires on any failed invocation "at the parse stage or anywhere
later". This is not a rediscovery of that ruling: the ruling's own justification at `ado:34-35` is
that "the stored e() results predate the user's latest (failed) attempt, so redisplaying them
silently would be misleading" — and after `estimates replay m1` **nothing predates anything**. The
e() in memory is exactly the estimation the user is asking to see; the failed invocation was
Stata's own post-estimation machinery, not a user estimation attempt. The premise is false for
this trigger and the refusal text asserts it anyway. The failed `estimates replay` runs through
wooldid's shell, its rc lands in `global WOOLDID_LASTRC` (`ado:40-44`), and the *working* route is
then refused:
`BARE BEFORE rc=0` -> `BARE AFTER STORE rc=0` -> `ESTIMATES REPLAY rc=198` (`WOOLDID_LASTRC` now
`[198]`) -> `BARE AFTER FAILED REPLAY rc=198` -> `estimates restore m1` -> `BARE AFTER RESTORE
rc=198` -> only after a refit does `BARE AFTER REFIT rc=0`. The refusal text is
"the last wooldid call failed with r(198); the stored results predate that failed call", which is
false: nothing about the stored estimation failed. The prober reported `RESTORE_RC=0, BARE2_RC=0`;
that does not reproduce. `estimates table` is unaffected (rc 0).

### FUZZ-05 the event-study PRE window reprices the ATT — **PARTIAL** (severity medium -> low)
repro: `repro/REPRO_F05_eswindow.do`

The falsifiable half of the claim is true — `esprelength()` alone does move the reported `att`.
The causal framing ("silently reprices the headline number") does not survive the discriminating
test the prober did not run.

Four ZERO-NOISE designs where the estimand is exactly identified, `esprelength(0/1/2/3)`:
- A balanced, homogeneous effect, i=unit: att = 2.0000000000 at every window (hex differs in the
  last 1-2 ulp), truth 2.
- B unbalanced (25% interior gaps), dynamic ramp, i=unit: 3.2312252964 at every window, truth
  3.2312252964.
- D unbalanced, dynamic, i=cohort, **no** unit heterogeneity: 3.2312252964 at every window.
- C unbalanced, dynamic, i=cohort, **with** unit fixed effects — the only design that moves:
  3.1568625983 -> 3.2103142551 -> 3.2289702229 -> 3.2381576431 against truth 3.2312252964. The
  narrow-window estimate is the BIASED one and the estimate walks monotonically TOWARD the truth
  as the pre-window widens. That is the coarse-`i` aggregation problem on an unbalanced panel
  (the recon gen file calls it "an omitted-variable problem of the USER's making"), surfaced by
  the window, not created by it.
- E noisy (sd 1.0, 150 units, cluster(i)): 3.2328 -> 3.2399 -> 3.2791 -> 3.2114 against truth
  3.1922, with se 0.0942 -> 0.1049 -> 0.1345 -> 0.1504. Largest move **0.35 SE**; relative moves
  0.2%-1.4%. The SE grows monotonically as the reference pool shrinks, which is the expected
  efficiency cost of spending pre-rows on lead dummies.

So: when the specification is right the att is invariant to machine precision; the movement the
prober measured is sampling variation of a less efficient specification plus (on a coarse-`i`
panel) pre-existing aggregation bias. The rule is already stated at `sthlp:1370`. A one-line
caution on `esprelength()` is a reasonable doc request, which is all this is. Severity low.

### FUZZ-06 dots(-5) refused under bootstrap(), accepted under permute() — **CONFIRMED** (low)
repro: `repro/REPRO_F06_dots.do`

`permute(shuffle) permreps(24) rseed(9) dots(-5)` -> rc 0, run completes, no message.
`bootstrap(standard) reps(24) rseed(9) dots(-5)` -> r(198) "dots() must be a nonnegative

### FUZZ-07 `update` on a full command line — **CONFIRMED from source, NOT EXECUTED**
repro: `repro/REPRO_F07_update.do` (the wooldid line is deliberately commented out)

`ado:555-563`: `wooldid_worker` parses its syntax line, then
`if "\`update'" == "update" { net install wooldid, from(https://raw.githubusercontent.com/
thegland/wooldid/main/wooldidinstall/) replace ; dis "Update complete; ..." ; exit }` —
unconditional, before `wooldid_validate`, so the estimation request on the same line is discarded
and nothing is posted to `e()`; the bare `exit` gives rc 0. I did **not** run it: it performs a
network package install with `replace` into the user's PLUS directory. Severity low.

### FUZZ-08 reversing the sort moves analytic SEs in the 8th significant digit — **PARTIAL / largely refuted as stated** (low)
repro: `repro/REPRO_F08_sortorder.do`

Pristine-twice first (the project's own doctrine): FWD1 == FWD2 bit-identical, REV1 == REV2
bit-identical. So no nondeterminism — good, the pairs are clean.

But the claimed *pattern* does not generalize and the claimed *magnitude* does not reproduce:
- Simple design (`pG_sort.log`): under `gsort -i -t` the **se is bit-identical**
  (`+1.60335fc695684X-004` both ways) while the **point estimate moves**
  (`...e990` -> `...e98b`, ~1e-15 relative). The claim says "point estimates invariant to 1e-16
  everywhere; three pairs moved derived columns".
- Hard design (ill-conditioned absorb, weights over ~3 orders of magnitude, near-collinear
  controls, cluster(region)): both move. `rel|db| = 7.8e-15` and `rel|dse| = 6.7e-12` at
  regtol(9); `2.3e-14` / `7.4e-11` at regtol(12) and regtol(13). That is **below the project's
  1e-10 indifference threshold** and ~350x smaller than the claimed 2.6e-8, which I could not
  reach on any of five designs.
- regtol does not shrink it (that part of the claim holds; it slightly enlarges it).
- A monotone id relabel (`i = i*7+3`) is **bit-identical**, so "relabelling the unit ids" is not
  by itself a mover.
- Attribution confirmed directly: plain `reghdfe y x1 [aw=fwt], absorb(i t) vce(robust) tol(1e-9)`
  forward vs reverse returns `b identical=0  se identical=0` on the same data. It is reghdfe.

## NEW FINDINGS (found while refuting)

### NEW-1 [medium/certain] The level round-trip through `c(level)` makes wooldid unusable at ~13% of legal session levels, and corrupts `c(level)` when it half-works
repro: `repro/REPRO_F03_level.do` (limb A) and `repro/REPRO_NEW_level_state.do` (limb B)

`wooldid_validate` fills an omitted `level()` from `c(level)` at **`ado:5507`**
(`if \`level' == 0 local level = c(level)`, added by CS-2 on 2026-09-06), and the shell/worker do
the same at `ado:575` (`global WOOLDID_LEVEL0 = c(level)`) and `ado:578`
(`local wdlvl = c(level)`). All three render at 16 significant digits, and the result is handed to
`set level`, which parses the literal text. `pF_level_trace.log` has the `set trace` proof: on a
call with no `level()` at a session level of 99.9, `ado:576` executes as
`set level 99.90000000000001` and fails, and `ado:70` then fails the same way.

**Limb A — the package is bricked at a hostile session level.** With `set level 99.9` in force and
**no `level()` option at all**, every form fails r(198) with "level() can have at most two digits
after the decimal point" printed twice: `att robust`, `att robust safety(off)`,
`att unconditionalse`, `att robust fastnose`. Plain `regress`, `reghdfe y x1, absorb(i t)` and
`margins, dydx()` are all rc 0 at the same session level, so this is wooldid's own re-render, not
a Stata-wide restriction. `set level 95` restores service. 1152 of the 9000 two-decimal levels in
[10,99.99] and 40 of the 100 one-decimal levels in [90,100) have this property; `set level 99.9`
in a `profile.do` is a legal, if uncommon, thing for an economist to have.

**Limb B — a successful estimation is reported as a failure and the session level is destroyed.**
With `set level 99.9` in force and a perfectly legal `level(95)`: the table prints, `e(cmd)=wooldid`,
`e(N)=600`, `e(level)=95` — the estimation succeeded and posted — and the command still exits
**r(198)**, because the shell's restore (`ado:69-71`) runs `set level 99.90000000000001`. It leaves
`c(level)` at **95** (the user's 99.9 is silently gone, and every subsequent Stata CI in the session
is at the wrong level), and leaks `WOOLDID_LEVEL0=[99.90000000000001]`. Control: at a benign session
level of 90 with `level(99)` the same call is rc 0 and `c(level)` returns to 90 correctly.

Why this is not just FUZZ-03: FUZZ-03 is "a level I asked for is refused". This is "a level I never
mentioned makes the command unusable", plus silent corruption of a Stata setting, plus a nonzero rc
on a run that in fact succeeded and posted (so `if _rc` guards in a user's loop will skip results
that are actually there).

### NEW-2 [low/probable] Inert options are announced inconsistently: one Caution, six silences, four refusals
repro: `repro/REPRO_F01_elasticity_header.do` (the COMPANION loop)

Two separate gates are involved and both are uneven. Keyed on **`makecfxplots`** (these are inert
with `contreat()` too): `cfxlattice(dose)` prints "Caution: cfxlattice() has no effect without
makecfxplots and is being ignored", while `cfxplottypes(0)`, `makecfxplotsbysg` and `cfxplotnose`
are accepted rc 0 with no message at all. Keyed on **`contreat()`**: `latticeignoreweights`,
`ccnoabsorb` (sthlp:1121 - it only moves the continuous-treatment controls out of `absorb()`) and
`contreatpoly(2)` are accepted rc 0 and silent, while `lattice()`, `contreatcontrols()`,
`contreatwithin` and `makecfxplots` are refused r(198). The project's published policy (quoted in
the shell comment at `ado:520-522`) is that "no accepted option is a silent no-op".
`contreatpoly(2)` is the one with a plausible consequence: a user can believe a quadratic dose was
fitted when there is no dose at all.

## NEGATIVE RESULTS (attacked, clean)

- **Run-to-run determinism.** Three pristine repeats of the same weighted, clustered, controlled,
  event-study call on identical data are bit-identical; so are two repeats on the reversed sort.
  Nothing in wooldid's own arithmetic is nondeterministic on these paths.
- **Monotone id relabelling** (`i = i*7+3`) leaves every reported column bit-identical.
- **`esprelength()` invariance** holds to 1-3 ulp on every correctly-specified zero-noise design
  I could build (balanced/homogeneous, balanced/dynamic, unbalanced/dynamic at i=unit,
  unbalanced/dynamic at i=cohort without unit heterogeneity), and the reported att equals the
  design truth exactly in all four.
- **`contreatelasticitytype(garbage)`** is refused r(198) even with no `contreat()`: the domain
  screen fires without a parent screen, exactly as `sthlp:908` promises.
- **`regtol()` is genuinely wired** to reghdfe's `tol(1e-\`regtol')` (`ado:1476`), so the prober's
  regtol legs were testing something real.
- **`i=unit` + `contreat()`** errors with a fully named wooldid message ("a treated cohort-period
  dummy coefficient was dropped for multicollinearity ... i == 59, relative-t == 2"), and
  `permreps(12)` and `permute()` without `cluster()` are both refused with precise, actionable
  wooldid text. No uninformative failures found on those paths.
